1.1 Overview of Bayesian Software

The rise of MCMC methods — catalysed by WinBUGS — transformed practical Bayesian statistics. Before software automation, Bayesian analyses required hand-derived full conditionals and custom code; WinBUGS made arbitrary graphical models accessible to applied researchers.

SoftwareLanguage / BackendStatus / Notes
WinBUGSBUGS, Windows GUIFinal version 1.4.3; no longer updated; installation issues on Windows 10
OpenBUGSBUGS (open source)Actively maintained; larger sampler set; supports censoring C() and truncation T()
JAGSBUGS dialect, C++Cross-platform; interfaced via rjags
NIMBLEBUGS + R extensions, C++Flexible MCMC config; write your own samplers/distributions
StanHMC / NUTS, C++Requires gradient info; highly efficient for complex models
Key progression: WinBUGS (click-and-point GUI) → batch mode via R2WinBUGS / R2OpenBUGS → JAGS / NIMBLE (fully scriptable, cross-platform, greater flexibility). The BUGS language is shared across WinBUGS, OpenBUGS, JAGS, and NIMBLE, so model code is largely portable.

Why batch mode?

Repetitive point-and-click interaction with WinBUGS is error-prone and non-reproducible. Batch processing via R scripts allows automatic looping over sensitivity analyses, reproducibility, and integration with downstream R-based reporting.

OpenBUGS extensions over WinBUGS

  • Larger class of sampling algorithms with improved blocking
  • Additional distributions and functions
  • Censoring: C(lower, upper) — likelihood contribution from censored observations
  • Truncation: T(lower, upper) — restricts a distribution to a bounded range
  • Detailed sampler diagnostics printed by default

NIMBLE: Key Differentiators

  • Almost identical model syntax to WinBUGS/JAGS — minimal porting effort
  • C++ compilation of models gives substantially faster sampling
  • Users can call existing R functions directly in model code
  • Users can implement custom distributions and samplers in R/C++
  • Full programmatic control over the MCMC configuration (change, add, or remove individual samplers)

1.2 WinBUGS and OpenBUGS — Workflow

Win/OpenBUGS operates through an .odc compound document — a single file that holds model code, data, and initial values. Opening this document in Win/OpenBUGS then proceeds through a fixed sequence of GUI steps.

Three Required Tools (in order)

StepToolMenu PathWhat it does
(a)Specification ToolModel → Specification…Load model, data, initial values; compile
(b)Sample Monitor ToolInference → Samples…Select parameters to track during sampling
(c)Update ToolModel → Update…Specify iterations and run the MCMC chain

Specification Tool — Four Sub-steps

  • Check model: Highlight the model{} block → click check model. Message: "model is syntactically correct."
  • Load data: Highlight the list(…) data block → click load data.
  • Compile: Click compile. For multiple chains, first set num of chains before compiling.
  • Load inits: Highlight each initial values list(…) → click load inits once per chain. Click gen inits if remaining inits are still needed.
Order matters: You must Check → Load Data → Compile → Load Inits in exactly this sequence. Skipping or reordering these steps causes error messages such as "model not compiled."

Sample Monitor Tool

  • Type node name → click set for each parameter to monitor. End with * → set to monitor all nodes.
  • After sampling: history (full trace), density (marginal posterior density), stats (summary statistics), auto corr (ACF), bgr diag (Gelman-Rubin convergence diagnostic).
  • Remove burn-in: fill in beg = 1001 (to discard first 1,000) then click history again.
  • Thinning: fill in thin = 10 — note this generates 10× the requested iterations.
Dynamic Trace: In WinBUGS, click trace before running to watch the chain evolve in real time. In OpenBUGS, run a small number of iterations first, then click trace.

1.2 The BUGS Language — Key Concepts

Osteoporosis Simple Linear Regression Example

Model: tbbmci ~ Normal(μi, τ), μi = β₀ + β₁ · bmii, with τ = 1/σ². The BUGS code structure:

model { for (i in 1:N) { tbbmc[i] ~ dnorm(mu[i], tau) ## likelihood (blue) mu[i] <- beta0 + beta1 * bmi[i] ## logical node (green) } sigma2 <- 1 / tau ## derived quantity (green) sigma <- sqrt(sigma2) beta0 ~ dnorm(0, 1.0E-6) ## priors (red) beta1 ~ dnorm(0, 1.0E-6) tau ~ dgamma(1.0E-3, 1.0E-3) } # data list(tbbmc=c(1.798, 2.588, ...), bmi=c(23.61, 30.48, ...), N=234) # initial values list(beta0=0.4, beta1=0.025, tau=1/0.05)

Three Types of Nodes

Node typeBUGS operatorRole
Stochastic (priors + likelihood)~Random variable; defines prior or likelihood
Logical (deterministic)<-Deterministic transformation of other nodes
Observed data~ (data provided)Likelihood term; value is fixed

Critical BUGS Conventions

  • Precision parameterization: dnorm(mu, tau) uses precision τ = 1/σ², not variance. Always specify variance parameters as tau ~ dgamma(…) and derive sigma via logical nodes.
  • Declarative language: Statement order does not matter — BUGS figures out the dependency graph (DAG) automatically.
  • No improper priors: Win/OpenBUGS does not accept improper priors (e.g., uniform on the whole real line). Use a very vague but proper prior such as dnorm(0, 1.0E-6).
  • No if-then-else: Use the step() and equals() functions instead.
  • Initial values: Do not specify initial values for logical nodes. It is advisable to always set initial values for variance parameters explicitly.
  • Vectors: Denoted by [] (e.g., beta[], bmi[]). Ranges: beta[1:6].

Vector / Matrix Operations (Multiple Regression)

mu[i] <- inprod(beta[], x[i,]) ## scalar product beta[1:6] ~ dmnorm(mu.beta[], prec.beta[,]) ## multivariate normal prior prec.beta[r,s] <- equals(r,s) * c ## diagonal precision (ridge)
Rectangular data format: When data is in table form, the table ends with END and must be loaded separately from the list() statement. Click load data for each part.

Convergence Acceleration Techniques

  • Centering/standardizing covariates: mu[i] <- beta0 + beta1*(bmi[i]-mean(bmi[]))/sd(bmi[]) — reduces posterior correlation between intercept and slope, dramatically improving mixing.
  • Blocking: Sample correlated coefficients jointly with a multivariate normal prior (dmnorm) to remove within-block correlations.
  • Over-relaxation: Switch on over relax in the Update Tool — negatively correlates successive draws to reduce autocorrelation.
  • Cross-correlation plot: Use bgr diag / cross-correlation output to diagnose problematic parameter correlations.
Ridge vs vague prior on β: Using a ridge normal prior (c = 5 instead of c = 1e-6) substantially reduces cross-correlations among regression coefficients, as visible in the cross-correlation plot — darker off-diagonal elements disappear.

1.2.2 BGR Convergence Diagnostic

The Brooks-Gelman-Rubin (BGR) diagnostic assesses convergence by comparing within-chain and between-chain variance across multiple chains started from overdispersed initial values.

  • Requires ≥ 2 chains (ideally 3–8), started from overdispersed initial values — intentionally far from the posterior mode.
  • The BGR ratio (red line) should converge to 1 as the chains mix. A value near 1 indicates the between-chain variance is no larger than the within-chain variance.
  • In WinBUGS: compile with multiple chains → load inits once per chain → after sampling, click bgr diag in the Sample Monitor Tool.
Reading the BGR plot: Three lines are shown for each parameter: (i) pooled posterior interval width, (ii) average within-chain interval width, and (iii) their ratio. Convergence is indicated when the ratio stabilizes near 1 and the two interval widths converge. The example in the slides shows convergence around iteration 500 for β₁ and σ².

Troubleshooting Win/OpenBUGS

Errors can occur at five stages: syntax checking, data loading, compilation, providing initial values, and running the sampler. The most disruptive error is the TRAP error — a crash of the OpenBUGS GUI, often caused by invalid initial values (e.g., initializing a standard deviation at a negative value) or an ill-specified model. Always consult the Tips and Troubleshooting section of the Win/OpenBUGS manual as a first resource.

1.3.1 Running OpenBUGS from R (R2OpenBUGS)

R2OpenBUGS replaces point-and-click by running OpenBUGS in script mode from R, making analyses reproducible and automatable. The workflow has 13 steps + a final interpretation step.

Steps 1–3: Setup and Data

install.packages("R2OpenBUGS"); install.packages("coda"); install.packages("readr") library("R2OpenBUGS"); library("coda"); library("readr") setwd("C:/root/Programs course") osteop <- read_delim("osteop.txt", " ", escape_double=FALSE, trim_ws=TRUE) head(osteop); summary(osteop)

Step 4: Write the Model

Two approaches: (a) write model to a .txt file and load with file.show(), or (b) embed model directly in R using cat():

cat("model { for (i in 1:N){ tbbmc[i] ~dnorm(mu[i],tau) mu[i] <- beta0+beta1*bmi[i] } sigma2 <- 1/tau beta0 ~ dnorm(0,1.0E-6) beta1 ~ dnorm(0,1.0E-6) tau ~ dgamma(1.0E-3,1.0E-3) }", file="osteo.model2.txt") file.show("osteo.model2.txt")

Steps 5–7: Data, Inits, Parameters

N <- length(osteop$tbbmc) my.data <- list(tbbmc=osteop$tbbmc, bmi=osteop$bmi, N=N) ## Explicit initial values for 3 chains: my.inits <- list( list(beta0=0.4, beta1=0.025, tau=1/0.05), list(beta0=0.4, beta1=0.055, tau=1/0.05), list(beta0=0.4, beta1=0.025, tau=1/0.12)) ## OR randomly generated: my.inits <- function()(list(beta0=rnorm(1,0.4,1), beta1=rnorm(1), tau=runif(1,0.5,1))) parameters <- c("beta0", "beta1", "sigma2")

Step 8: Run the MCMC Chain

osteo.sim <- bugs(data=my.data, inits=my.inits, parameters.to.save=parameters, "osteo.model.txt", n.chains=3, n.iter=1500, n.burnin=750, n.thin=1, OpenBUGS.pgm="c:/Program Files (x86)/OpenBUGS/OpenBUGS323/OpenBUGS.exe", working.directory=wd, clearWD=FALSE, debug=TRUE, DIC=TRUE)
Key arguments:
  • n.iter: total iterations per chain (includes burn-in)
  • n.burnin: iterations to discard from start (default = 50% of n.iter)
  • n.thin: thinning factor — retain every n.thin-th draw
  • debug=TRUE: waits for user signal before returning to R, so you can inspect the OpenBUGS window
  • DIC=TRUE: compute the Deviance Information Criterion
  • clearWD=FALSE: retains the OpenBUGS log files in the working directory

Steps 9–13: Summaries and Diagnostics

## General output print(osteo.sim); plot(osteo.sim) ## Convert to mcmc.list for CODA osteo.mcmc <- as.mcmc.list(osteo.sim) plot(osteo.mcmc); summary(osteo.mcmc) ## CODA diagnostics traceplot(osteo.mcmc) # trace plots cumuplot(osteo.mcmc, ask=FALSE) # running mean plots acfplot(osteo.mcmc) # ACF plot autocorr(osteo.mcmc) # ACF values crosscorr.plot(osteo.mcmc) # cross-correlation densplot(osteo.mcmc) # marginal density plots effectiveSize(osteo.mcmc) # effective sample size HPDinterval(osteo.mcmc) # HPD credible intervals ## Convergence tests gelman.diag(osteo.mcmc) gelman.plot(osteo.mcmc, ask=FALSE) geweke.diag(osteo.mcmc) geweke.plot(osteo.mcmc, ask=FALSE)

1.3.2 Running JAGS from R (rjags)

JAGS ("Just Another Gibbs Sampler", Plummer 2011) is written in C++ and runs on all major operating systems. The model syntax is a dialect of BUGS. The R workflow uses two-stage sampling: first build the model object, then draw samples.

Steps 1–7

Identical to the R2OpenBUGS workflow: install/load packages (rjags, coda, readr), load data, write the model, prepare data list, prepare initial values, and collect parameter names.

Package note: The slide shows install.packages("R2OpenBUGS") in the JAGS section — this appears to be a copy-paste artefact. For JAGS, the correct package to install is rjags. Both coda and readr are still required.

Step 8: Two-Stage Sampling in JAGS

## Stage 1: Build model object (compiles + runs adaptation) jags <- jags.model(file="osteo.model.txt", data=my.data, inits=my.inits, n.chains=3) ## Stage 2: Draw samples osteo.sim <- coda.samples(model=jags, variable.names=parameters, n.iter=1500, thin=1)
JAGS vs R2OpenBUGS: JAGS does not require a path to an external executable — it is a pure R package. The two-stage approach (build then sample) separates model compilation from sampling, making it easy to run multiple rounds of sampling on the same compiled model. coda.samples() returns an mcmc.list object directly, so conversion is not needed.

Steps 9–13 and Final Step

Identical to R2OpenBUGS: print, plot, summary, all CODA functions (traceplot, effectiveSize, HPDinterval, gelman.diag, geweke.diag, etc.), then interpret results.

1.3.3 Running NIMBLE from R

NIMBLE ("Numerical Inference for statistical Models using Bayesian and Likelihood Estimation") extends BUGS with a programmable interface and C++ compilation. It is the most flexible of the three R-based options covered.

Key Differences from JAGS / R2OpenBUGS

  • Model code is written inside nimbleCode({ … }) directly in R — no separate text file required.
  • Data and constants are supplied separately: my.data (observed random variables) vs my.constants (fixed values like N). This distinction matters for C++ compilation.
  • The sampling call is nimbleMCMC() with the argument samplesAsCodaMCMC=TRUE to return an mcmc.list.

Step 4: Model Specification

model <- nimbleCode({ for (i in 1:N){ tbbmc[i] ~dnorm(mu[i], tau) mu[i] <- beta0 + beta1 * bmi[i] } sigma2 <- 1 / tau sigma <- sqrt(sigma2) beta0 ~ dnorm(0, 1.0E-6) beta1 ~ dnorm(0, 1.0E-6) tau ~ dgamma(1.0E-3, 1.0E-3) })

Steps 5–6: Data and Constants

N <- length(osteop$tbbmc) my.data <- list(tbbmc=osteop$tbbmc, bmi=osteop$bmi) # stochastic nodes my.constants <- list(N=N) # fixed constants

Step 8: Running nimbleMCMC

osteo.sim <- nimbleMCMC( code=model, data=my.data, constants=my.constants, inits=my.inits, monitors=parameters, niter=1500, nburnin=750, nchains=3, thin=1, samplesAsCodaMCMC=TRUE)
samplesAsCodaMCMC=TRUE: This argument makes nimbleMCMC() return an mcmc.list object directly, so all standard CODA functions (traceplot, effectiveSize, gelman.diag, etc.) apply immediately without conversion.

1.4 Summarising the MCMC Chain

Post-sampling summarisation is done primarily with the coda package. All three workflows (R2OpenBUGS, JAGS, NIMBLE) converge to an mcmc.list object as the common input to CODA functions.

Combining Chains

library(runjags) osteo.combined <- combine.mcmc(osteo.mcmc) HPDinterval(osteo.combined) # HPD interval on combined chain
Why combine? Most CODA functions (e.g., summary, densplot) process each chain separately. Combining chains with combine.mcmc() pools all posterior draws into a single chain, which is needed for functions like HPDinterval that operate on a single sample.

MCMCvis Package

library(MCMCvis) MCMCplot(object=osteo.mcmc) # caterpillar plot MCMCtrace(object=osteo.mcmc, iter=4000, pdf=FALSE, params=parameters, type="trace") # trace plot MCMCtrace(object=osteo.mcmc, iter=4000, pdf=FALSE, ind=TRUE, params=parameters, type="density") # density by chain MCMCpstr(mcmc.output, func=function(x) sd(x)/sqrt(length(x))) # MCSE MCMCsummary(object=osteo.mcmc, round=2) # table summary MCMCsummary(object=osteo.mcmc, round=2, HPD=TRUE, hpd_prob=0.95) # with HPD intervals

ggmcmc Package

library(ggmcmc) out.ggs <- ggs(osteo.mcmc) # convert to ggs object ggs_histogram(out.ggs) # posterior histograms ggs_traceplot(out.ggs) # trace plots ggs_running(out.ggs) # running mean plots ggs_compare_partial(out.ggs) # chain comparison ggs_geweke(out.ggs) # Geweke diagnostic ggs_pairs(out.ggs) # bivariate scatter plots ggs_autocorrelation(out.ggs) # ACF ggs_caterpillar(out.ggs) # credible interval plot ggs_crosscorrelation(out.ggs) # cross-correlation matrix ggs_density(out.ggs) # density plots ggs_diagnostics(out.ggs) # combined diagnostics
