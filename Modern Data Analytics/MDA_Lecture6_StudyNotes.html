1 · Introduction — Infrastructure for Data Science

This lecture is Part III of the Modern Data Analytics course. The goal is to understand the infrastructure needed to move from raw data all the way to actionable insights, focusing on structure and principles rather than individual tools.

Conceptual Model — four pillars of a Data & Analytics System:
  • Collection — APIs, databases, raw files, web scraping
  • Storage — structured (SQL tables) and unstructured (S3, blob) data
  • Processing — transformation, aggregation, modelling
  • Serving — APIs, MCPs, dashboards
Machine Learning projects additionally need: data/model versioning & monitoring, experiment tracking, and model deployment.

Educational vs. Production Context

In academic projects, pipelines typically live inside a single notebook with no monitoring, clean code focus, and data & modelling logic interleaved. Production environments are radically different:

DimensionEducational (Notebook)Production (Industry)
StructureSingle notebookModular scripts / services
MonitoringNoneLineage, reproducibility
AutomationManual runsScheduled orchestration
VersioningRarelyEssential (code, data, model)
⚠ Jupyter Notebooks in Production — While you can build infrastructure around notebooks (see Netflix's Papermill approach), there are significant issues: hidden state, poor version control, difficult testing, and no built-in dependency management.

2 · Data Pipelines

A data pipeline is a collection of transformations \((v_1, v_2, \ldots, v_n)\) applied to data, where the output of one stage feeds the next.

Definition — Data Pipeline:
A sequence of processing steps where each step produces output consumed by subsequent steps. Pipelines are formally represented as Directed Acyclic Graphs (DAGs).

DAG Representation

  • Vertices (nodes) — modular components that perform a data transformation
  • Edges — dependencies across transformations (v produces output consumed by u)
  • Acyclicity — no circular dependencies; execution has a guaranteed topological order
✦ Concrete Example (Air Quality Predictor):
Monitor Locations → Weather API & Air Quality API → Preprocess & Combine → Load to Database

A second sub-pipeline: Retrain Predictive Model → Evaluate Model → Deploy (MLflow) / Add experiment trace (MLflow)

3 · DAG Optimization Techniques

Given graph \(G = (V, E)\) with \(\mathcal{T}_v\) = execution time of task \(v\), and path length \(L(P) = \sum_{i=1}^{k} \tau(v_i)\):

Q1 — Minimum Pipeline Runtime → Critical Path Analysis

\[ L^* = \max_{P \in \text{paths}} L(P) \]
The critical path is the longest path through the DAG. No amount of parallelisation can beat it — it is a hard lower bound on total runtime.

Q2 — Parallelisable Tasks → Anti-Chain Analysis

Partial Order: \(u \prec v \iff\) there is a directed path from \(u\) to \(v\).
Anti-chain: A subset of vertices where no two nodes are related by \(\prec\) — i.e., they have no dependency on each other and can run in parallel.

The size of the largest anti-chain gives an upper-bound on the number of workers needed to achieve maximum parallelism (Dilworth's theorem).

✦ Example (5-node DAG \(V = \{v_1,\ldots,v_5\}\)):
With \(v_1 \prec v_2, v_3, v_4, v_5\); \(v_2 \prec v_4, v_5\); \(v_3 \prec v_4, v_5\); \(v_4 \prec v_5\), the only anti-chain is \(\{v_2, v_3\}\) → at most 2 tasks can run concurrently.

Q3 — Minimal Dependencies → Transitive Reduction

Transitive reduction gives the minimal dependency graph \(G'\) that preserves all execution constraints:

\[ u \prec v \text{ in } G \iff u \prec v \text{ in } G' \]

What remains is the minimal structure from which we can derive data contracts — the explicit input/output agreements between tasks.

Minimum runtime?Critical Path Analysis\(L^* = \max_{P} L(P)\)
Max parallelism?Anti-Chain AnalysisSize of largest anti-chain

4 · Pipeline Orchestration

Orchestration refers to what order and at what times data pipelines should be run. It is the gap between a collection of processing scripts and a reliable production data system.

What orchestrators provide:
  • Explicit dependencies through DAG definition
  • Automatic scheduling and execution
  • Retries on failure
  • Visibility on process executions (monitoring & logs)
Critical distinction: Orchestrators do NOT process data themselves — they coordinate when and in what order data-processing tasks run.

Apache Airflow

The most popular pipeline orchestrator. It natively implements DAGs, dependencies, and scheduling. A DAG in Airflow is defined as a Python function decorated with @dag, and individual tasks are Python functions decorated with @task.

✦ Airflow DAG Structure:
@dag(schedule='@daily', start_date=datetime(2026,1,1), catchup=False)
Tasks are defined inside using @task, and dependencies are expressed by passing outputs as inputs between function calls.

Airflow's UI provides: past runs & failures, manual triggering, execution time charts, logs, SLA monitoring, and links to data assets.

Alternatives to Airflow

Prefect, Dagster, AWS Step Functions, Argo, Luigi — each with trade-offs in complexity, cloud integration, and observability.

What can tasks be?

Python functions, SQL commands, DBT scripts, bash commands, external triggers (emails, notifications), human-in-the-loop verification steps, and more.

5 · Model Development & MLOps

Building a model (experimentation) and deploying it (production) require fundamentally different mindsets:

PhasePrimary ConcernKey Metrics
DevelopmentExperimentation — try many thingsModel performance, iteration speed
ProductionConsistency & auditabilityReliability, reproducibility, latency

MLOps Stack

The ML process is still a pipeline (Raw Data → Preprocessing → Training → Candidate Model → Deployment), but requires additional infrastructure: experiment tracking, model versioning, deployment pipelines, and prediction monitoring.

For each experiment run, you must track:
  • Which code version was used
  • What data was used
  • What hyperparameters were set
  • Which algorithm was applied
  • Any metadata (random seeds, execution times)
All of this must be linked to evaluation metrics to enable reproducibility.

6 · MLflow — Experiment Tracking & Model Registry

MLflow is an open-source tool for end-to-end ML project management. It has two key components:

6.1 Tracking Server

Logs parameters, metrics, artifacts, and metadata for every experiment run. Using mlflow.sklearn.autolog(), Scikit-learn experiments are tracked automatically. The UI lets you compare runs across experiments via visualisations (parallel coordinates, scatter, box plots).

✦ Python integration:
import mlflow
mlflow.sklearn.autolog()
with mlflow.start_run():
    model.fit(X_train, y_train)

6.2 Model Registry

Once experimentation is complete, the model registry tracks versions and deployments. The champion alias marks the model version currently serving in production. Models are pickled by default.

⚠ Pickle Security Note: MLflow pickles models by default. Pickle files can execute arbitrary code upon loading — always validate the provenance of model artifacts before loading in production.

6.3 Model Deployment via MLflow

MLflow also supports deployment: mlflow deployments wraps the model in a Docker container and can target Databricks Model Serving, Amazon SageMaker, Azure ML, Kubernetes clusters, or local Flask/batch inference.

7 · Serving — Making Data & Models Available

After pipelines are reliable and models are versioned, the next challenge is how to expose them to end users without giving raw database access.

What we do NOT want in production:
  • Unrestricted direct access to Python objects or database tables
  • Users knowing internal storage details or model characteristics

Service Layer Pattern

A dedicated service layer (typically a REST API) sits between the internal data/models and consumers. The data engineering team builds and maintains this layer; business stakeholders and external systems consume data and predictions through it.

✦ Minimal FastAPI Example:
from fastapi import FastAPI
app = FastAPI()
@app.get("/data")
def get_data(): return {"data": "Hello, World!"}

The service layer has direct access to internal data and models. Users get granular access-management policies — they only see what they're authorised to see.

8 · Serving in the Age of Agentic AI

Increasingly, organisations expose data and models not just to human consumers via REST APIs, but to AI agents via MCP (Model Context Protocol) servers.

MCP Architecture:
  • MCP Hosts — AI assistants or IDEs that initiate connections
  • MCP Clients — connectors within the host that maintain 1:1 connections with servers
  • MCP Servers — services that provide context and capabilities through the standardised protocol
✦ MCP Server Creation (Python):
@tool("get_list_of_locations", "Returns a list of locations with bike tracking points...")
async def get_list_of_locations(args): ...
mcp_server = create_sdk_mcp_server(name="example_mcp", tools=[get_list_of_locations])

MCP servers share the same general structure as REST APIs, but add a readable natural-language description of each endpoint so that AI agents can understand what the tool does and when to call it.

Key insight: If an organisation already has a well-structured data system with REST APIs, exposing it via MCP for agentic AI consumption is straightforward — the same data contracts and service patterns apply.
