1. What is Cloud Computing?

Cloud computing is on-demand access to computing resources (compute, storage, databases, analytics, AI tools, and more) delivered over the internet, typically on a pay-per-use basis. It is foundational to modern data science and MLOps.

Historical Evolution

EraModelKey characteristic
1980s–1990sOn-premises data centersServers privately owned & maintained by the company; physical access required
1990s–2000sInternet / web-based hostingAccess via browser over internet; but still own maintenance; no physical proximity needed
2000s–2010sVirtualization & cloudAmazon, Microsoft, Google build massive data centers; companies rent virtualized resources on demand; focus on core business, not IT management
Motivating example: Training a large ML model locally takes 10 hours. The same training job on AWS (e.g., a GPU-equipped EC2 instance) can take 30 minutes — a 20× speedup without buying any hardware.

Key Benefits for Data Science

BenefitWhat it means in practice
ScalabilityIncrease compute power on demand for large training jobs, then scale back down
FlexibilityRun notebooks, pipelines, and models from anywhere in the world
Cost efficiencyPay only for the resources you actually use — no capital expenditure on hardware

Common Data Science Use Cases

  • Storing and querying large datasets (e.g., S3, BigQuery)
  • ML training at scale (e.g., SageMaker, Vertex AI)
  • Data engineering and ETL pipelines (e.g., AWS Glue, Dataflow)
  • Model deployment and monitoring (e.g., Lambda + API Gateway)
  • Real-time analytics (e.g., Kinesis, Pub/Sub)

3. Cloud Service Models

Cloud service models define the level of control and responsibility the user has. The further up the stack, the less you manage — but also the less flexibility you have.

The Five Models Side-by-Side

ModelFull nameWhat the cloud managesWhat you manageAnalogy
IaaSInfrastructure as a ServiceHardware, networking, virtualisationOS, runtime, apps, dataRenting a raw kitchen with equipment — you cook from scratch
PaaSPlatform as a ServiceHardware + OS + runtime + middlewareYour code and dataRenting a kitchen with chef tools and pre-set ingredients — you just follow the recipe
SaaSSoftware as a ServiceEverythingJust your data & usageGoing to a restaurant — food is ready, you just eat
FaaSFunction as a ServiceServers, scaling, execution environmentJust your function codeMotion-sensor light — turns on only when triggered; off (and free) otherwise
CaaSContainer as a ServiceContainer orchestration infrastructureYour container imageShipping containers on a managed port — you pack the box, port manages logistics

IaaS — Infrastructure as a Service

DS scenario: Your laptop is too slow to train a model on a huge dataset. With IaaS (e.g., AWS EC2), you rent a GPU-powered VM, install Python/Jupyter/scikit-learn, train the model, then shut it down. You pay only for those hours — no hardware purchase.

Advantages: Full control over environment; any software can be installed. Disadvantages: More management overhead (OS patching, security).

Examples: EC2 (AWS), Azure Virtual Machine, Google Compute Engine — all IaaS.

PaaS — Platform as a Service

DS scenario: You built a web app exposing your ML model. With PaaS (e.g., Google App Engine), upload your code; the platform runs it, scales it, and keeps it secure — you never touch a server.

Advantages: Fast deployment; no infrastructure management. Disadvantages: Less flexibility than IaaS.

Examples: AWS Elastic Beanstalk, Google App Engine, Azure App Services.

SaaS — Software as a Service

DS scenario: You want to train a model without writing infrastructure code. Use Google Colab, DataRobot, or BigML — upload data, click to train, download results. Zero setup.

Advantages: No setup or maintenance; accessible from anywhere. Disadvantages: Minimal customisation.

Examples: Google Workspace, Tableau Online, Salesforce, Google Colab.

FaaS — Function as a Service (Serverless)

DS scenario: Serve a trained model. Deploy a predict(input_data) function via AWS Lambda. When a user submits data, the cloud runs the function and returns the prediction. When idle: nothing runs, nothing is billed.

Advantages: Cost-efficient for intermittent workloads; auto-scales. Disadvantages: Cold start latency; limited max runtime duration.

Examples: AWS Lambda, Google Cloud Functions, Azure Functions.

CaaS — Container as a Service

DS scenario: Your model depends on a specific version of pandas and scikit-learn. Package it all in a Docker container, then deploy to AWS Fargate or Google Cloud Run. The platform runs and scales the container without you managing servers.

Advantages: Flexible, portable, easy migration between platforms. Disadvantages: Requires container orchestration knowledge.

Examples: AWS ECS/Fargate, Google Kubernetes Engine (GKE), Azure Kubernetes Service (AKS).

Key exam distinction: CaaS combines benefits of IaaS (you control the container environment) and PaaS (the cloud manages the execution/scaling). It bridges the gap between full control and managed convenience.

Setting Up Billing Alarms (CloudWatch)

To monitor costs and avoid overage on the Free Tier:

  1. Go to Billing and Cost Management → Billing Preferences → enable CloudWatch Billing Alerts
  2. Set region to US East (N. Virginia) — billing metric data is only stored here
  3. Create a CloudWatch alarm: Billing → Total Estimated Charge → set threshold (e.g., $1) → link to SNS topic for email notification
The billing alarm only notifies you when the threshold is exceeded — it does NOT stop or pause your usage automatically.

6. Accessing AWS: Console · CLI · SDK

1. Management Console

Web-based GUI at aws.amazon.com. Best for beginners, manual setup, and visual exploration of services. Actions include drag-and-drop S3 uploads, clicking through SageMaker to launch notebooks, or creating Lambda functions via wizard.

2. CLI — Command-Line Interface

Text-based terminal tool. Fast for batch tasks and scripting. Must be installed locally and configured with credentials.

# Configure CLI with your IAM credentials
aws configure
# → Enter: Access Key ID, Secret Access Key, Region, Output format

# Example: copy a file to S3
aws s3 cp myfile.csv s3://my-bucket/

# Create an S3 bucket
aws s3api create-bucket --bucket my-bucket --region eu-central-1 \
  --create-bucket-configuration LocationConstraint=eu-central-1

3. SDK — boto3 (Python)

Programming library for interacting with AWS in Python code. Best for automation, custom workflows, and integration into data science pipelines.

import boto3

# Create S3 client (credentials via environment variables — safer than hard-coding)
s3 = boto3.client('s3')

# Upload a file
s3.upload_file('train.csv', 'my-bucket', 'train.csv')

# Read directly into pandas
import pandas as pd
df = pd.read_csv('s3://my-bucket/train.csv')
Never hard-code AWS credentials in Python scripts that are shared or version-controlled. Use environment variables (export AWS_ACCESS_KEY_ID=...) or IAM roles instead. boto3 automatically reads these.
S3 access control: By default, all S3 buckets and objects are NOT publicly accessible. To make objects public, you must explicitly disable "Block Public Access" settings and adjust bucket/object permissions. This is a deliberate security default.

AWS Lambda — Key Concepts

AWS Lambda lets you run code (Python, Java, Node.js, etc.) without provisioning servers. Code runs in response to events (e.g., HTTP requests, S3 uploads). You pay only for execution time.

Lambda function structure:

def lambda_handler(event, context):
    # event: input data (e.g., JSON body of HTTP request)
    # context: metadata (function name, timeout, etc.)
    input_data = pd.DataFrame([event['features']])
    prediction = model.predict(input_data)[0]
    return {'statusCode': 200, 'body': json.dumps({'prediction': int(prediction)})}

Three Lambda cost drivers: number of executions/month · memory allocated · execution time (ms). Free tier: 1 million requests/month + 400,000 GB-seconds of compute/month.

Lambda requires permission to read from S3. Attach an IAM policy granting s3:GetObject on the relevant bucket ARN to the Lambda execution role.

API Gateway — Key Concepts

API Gateway acts as the "front door" for your deployed model. It receives HTTP requests (from browsers, apps, Postman), forwards them to the Lambda function, and returns the response — without the caller ever touching Lambda or S3 directly.
Request flow:
User sends: POST https://<api-id>.execute-api.us-east-1.amazonaws.com/prod/predict
with body {"features": [22, 1, 7.25, 1, 0, 0, 1, 0, 0]}
→ API Gateway → Lambda loads model from S3, runs prediction → returns {"prediction": 0}

API Gateway advantages: user-friendly interface for your model · API key / token security · handles thousands of concurrent requests · built-in monitoring (request count, latency).

Model Serialisation with joblib

import joblib

# Save (serialise)
joblib.dump(model, 'model.pkl')

# Load (deserialise)
model = joblib.load('model.pkl')

Serialisation converts a Python object (trained model) into a binary file that can be saved and uploaded to the cloud. Deserialisation reconstructs the model object from that binary file — as done inside the Lambda function.

Short Answer — 10 Questions (Oral Exam Style)

Short Answer 1 · Concept
Explain the evolution from on-premises data centres to cloud computing. What limitations of earlier models drove organisations to adopt cloud infrastructure?
Model Answer: In the 1980s–1990s, organisations ran on-premises data centres — privately owned servers managed entirely by the company. Physical access was required; if a developer needed to use the server, they had to be in the same building. This model was capital-intensive and inflexible.

The 1990s–2000s introduced internet/web-based hosting, eliminating the need for physical proximity — apps were deployed on servers accessible over the internet via browsers. However, companies still owned and maintained the infrastructure.

The 2000s–2010s marked the cloud revolution: Amazon, Microsoft, and Google built massive shared data centres. Virtualisation technology allowed multiple organisations to share the same physical hardware in isolated environments, billed on a pay-per-use basis. Key drivers of adoption were: eliminating hardware capital expenditure, outsourcing IT management to focus on core business, elastic scalability (scale up for peaks, down for troughs), and global accessibility.

Likely follow-up questions:
  • What specific problems does cloud computing create that on-premises did not have?
  • When might a company still prefer on-premises over cloud for data science?
  • What is the difference between a public cloud, private cloud, and hybrid cloud?
Short Answer 2 · Service Models
Compare IaaS, PaaS, and FaaS using a concrete data science scenario for each. What is the key trade-off between control and convenience across these models?
Model Answer: IaaS (Infrastructure as a Service): A data scientist rents an AWS EC2 GPU instance to train a deep learning model. They install CUDA, Python, PyTorch, and custom libraries. After training, they terminate the instance. Full control over the environment — but responsible for OS, security patches, and configuration. Trade-off: maximum flexibility, maximum management overhead.

PaaS (Platform as a Service): A team deploys a Flask API exposing their model predictions on Google App Engine. They upload code; the platform manages servers, scaling, and updates. Trade-off: fast deployment, no server management — but limited to the runtimes and configurations the platform supports.

FaaS (Function as a Service): A team deploys a single predict() function on AWS Lambda, triggered by HTTP requests via API Gateway. When no requests come in, nothing runs and nothing is billed. Trade-off: extremely cost-efficient for intermittent workloads, fully managed — but limited runtime duration and cold start latency can be problematic for time-sensitive inference.

Core trade-off: Moving from IaaS → PaaS → FaaS reduces management burden but also reduces control and flexibility. IaaS is right for complex custom environments; FaaS is right when you just want to run a function without thinking about infrastructure at all.

Likely follow-up questions:
  • Where does SaaS fit in this spectrum, and can a data scientist use SaaS for model training?
  • What is a "cold start" in FaaS and how can it be mitigated?
  • Why might CaaS be preferred over pure FaaS for a complex ML pipeline?
Short Answer 3 · Providers
Compare AWS, Azure, and GCP from a data science perspective. In what scenarios might you choose each, and what factors should drive the decision?
Model Answer: AWS is the largest provider with the broadest ecosystem (200+ services). It excels in breadth — EC2 for compute, S3 for storage, SageMaker for end-to-end ML, Lambda for serverless. Choose AWS when: your team has existing AWS expertise, you need the widest service catalogue, or you're running an end-to-end ML pipeline (the lecture's own project uses AWS). The Free Tier is also generous for learning.

Microsoft Azure shines for organisations already in the Microsoft ecosystem (Windows, Office 365, Active Directory). Its hybrid cloud capabilities make it strong for enterprises that need to connect on-premises systems to cloud workloads. Azure ML supports Jupyter notebooks, containers, and Kubernetes. Preferred in regulated industries (government, healthcare, finance) for its compliance certifications.

GCP's Kubernetes tooling is top-tier (it created Kubernetes). Preferred when your primary workloads are large-scale data analytics or you rely heavily on Kubernetes.

Key decision factors: existing tools and integrations; team familiarity; budget; compliance requirements; specific service quality (e.g., data warehouse → BigQuery wins); geographic availability.

Short Answer 4 · AWS IAM & Security
Describe the five-step AWS security setup recommended in the lecture. Why is each step important, and what risks do they collectively mitigate?
Model Answer:
  1. Access IAM service: Centralises all security management. IAM is both the authentication (verifying identity) and authorisation (defining permissions) layer for all AWS services.
  2. Activate MFA on the root account: The root account has unrestricted access to everything and is linked to your credit card. Enabling MFA (e.g., Google Authenticator) means even if someone obtains your password, they cannot log in without the second factor. This is the single most impactful security step.
  3. Create an IAM user: Best practice is to never use the root account for daily tasks. An IAM user has only the permissions explicitly granted, limiting the blast radius of any compromise.
  4. Create a group and assign permissions: Grouping users with shared roles (e.g., "aws-admins") makes permission management scalable. Policies attached to the group apply to all members — no need to update each user individually.
  5. Create a password policy: Enforces minimum complexity (length, special characters, rotation) for all IAM users, reducing the risk of brute-force attacks.
Collectively, these steps enforce the principle of least privilege — each entity has only the minimum permissions required — and add defence-in-depth layers against account compromise.

  • How do IAM roles differ from access keys, and which should be preferred for Lambda functions?

Short Answer 6 · AWS Lambda
Explain how AWS Lambda works, including its pricing model, the structure of the handler function, and its advantages and disadvantages for serving machine learning model predictions.
Model Answer: AWS Lambda is a serverless, event-driven compute service. You upload function code (Python, Java, Node.js, etc.) and specify the handler. AWS runs the function in response to triggers — HTTP requests (via API Gateway), S3 events, scheduled timers, etc. — and scales automatically. When idle, nothing runs and nothing is billed.

Handler structure:
def lambda_handler(event, context):
  # event: input data (e.g., JSON from HTTP request)
  # context: metadata (function name, timeout remaining)
  prediction = model.predict(...)
  return {'statusCode': 200, 'body': json.dumps({'prediction': int(prediction)})}
Pricing: Three cost drivers — (1) number of executions/month, (2) memory allocated, (3) execution time in milliseconds. Free tier: 1M requests + 400,000 GB-seconds/month.

ML serving advantages: No server management; auto-scales with traffic; extremely cost-efficient for sporadic/low-volume prediction requests; pairs naturally with API Gateway for a complete REST endpoint.

Disadvantages: Cold start latency (first invocation after idle period takes seconds while the execution environment initialises); limited max runtime (15 min); limited storage; large ML libraries (PyTorch, TensorFlow) may exceed deployment package size limits — use Lambda Layers or container images instead.

Short Answer 7 · S3 and Data Management
Describe Amazon S3's role in a data science workflow. Explain what object storage is, how S3 access control works by default, and how a data scientist can read an S3 file directly into a pandas DataFrame.
Model Answer: Amazon S3 (Simple Storage Service) is the primary cloud storage layer for data science on AWS. It is object storage — data is stored as flat objects (files) in buckets, identified by a key (path). Unlike block storage (virtual hard drives) or file storage (shared filesystems), object storage is highly scalable, durable, and inexpensive — ideal for datasets, model artefacts, logs, and backups of any size.

Role in a DS workflow: S3 serves as the central data lake. Raw data is uploaded → SageMaker or EC2 reads from S3 for training → trained models are serialised (e.g., model.pkl) and uploaded to S3 → Lambda loads the model from S3 at prediction time.

Access control: By default, all buckets and objects are private — not accessible by anyone except the account owner. To allow public access, you must explicitly disable "Block Public Access" settings and configure bucket/object ACLs or policies. This is a deliberate security default to prevent accidental data exposure.

Reading into pandas:
# Route 1: HTTPS URL (requires public access enabled)
df = pd.read_csv('https://mybucket.s3.eu-central-1.amazonaws.com/data.csv')

# Route 2: S3 URI (requires boto3 + s3fs configured, or IAM credentials)
df = pd.read_csv('s3://mybucket/data.csv')

Short Answer 8 · API Gateway + Lambda Architecture
Explain the full request-response flow when a user sends a prediction request through an API Gateway + Lambda architecture (as in the Titanic project). What does each component do, and why is this architecture preferable to exposing Lambda directly?
Model Answer: Full flow:
  1. User sends POST https://<api-id>.execute-api.amazonaws.com/prod/predict with JSON body {"features": [22, 1, 7.25, ...]}
  2. API Gateway receives the HTTP request and validates it (optionally checks API keys or auth tokens)
  3. API Gateway forwards the request body to the configured Lambda function (AWS_PROXY integration)
  4. Lambda's lambda_handler(event, context) receives the event, loads the model from S3 (or uses a cached copy from /tmp/), runs inference, and returns a response dict with a status code and body
  5. API Gateway packages the Lambda response as an HTTP response and sends it back to the user
  6. User receives {"prediction": 0}
Why not expose Lambda directly? Lambda functions are not HTTP endpoints — they have no URL by default. API Gateway adds the HTTP layer, and with it: authentication/authorisation (API keys, OAuth), rate limiting, request/response transformation, monitoring dashboards (latency, error rate), SSL/TLS termination, and CORS handling. It also decouples the caller from the backend, so Lambda can be swapped for another implementation without changing the public API.

Short Answer 9 · Cost Management
Describe the AWS Free Tier in detail and explain the complete process for setting up billing alarms. Why are billing controls especially important for students or data scientists learning AWS?
Model Answer: AWS Free Tier types:
  • Always Free — available to all accounts indefinitely. Examples: Lambda (1M requests/month, 400K GB-seconds); DynamoDB (5 GB storage).
  • 12-Month Free — for new accounts, valid 12 months from signup. Examples: EC2 (750 hrs/month t2.micro), S3 (5 GB standard storage), RDS (750 hrs/month db.t2.micro).
  • Short-term Trials — some services offer a limited free trial period once activated.
Billing alarm setup:
  1. Go to Billing and Cost Management → Billing Preferences → enable "Receive CloudWatch Billing Alerts"
  2. Switch AWS region to US East (N. Virginia) — billing data is only stored here
  3. In CloudWatch: Alarms → Create Alarm → Billing → Total Estimated Charge → set threshold (e.g., $1 USD) → configure SNS topic for email notification → name and create alarm
Critical nuance: The alarm only sends a notification — it does NOT stop or pause usage. It is the user's responsibility to stop services manually after receiving the alert.

Why important for students: Leaving a SageMaker notebook instance, EC2 instance, or RDS database running unintentionally can rapidly accrue charges. A GPU EC2 instance can cost $0.90–$3+/hour. A student who forgets to shut down for a weekend could incur $50–$200 in unexpected charges. Billing alerts provide an early warning; understanding the free tier limits prevents accidental overage.
