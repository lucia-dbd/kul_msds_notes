1. Scalability and the Data Science Pipeline

Scalability is the use of different tools and architectures to scale data science applications so that they keep working as the volume of data — or the volume of requests — grows beyond what a single machine can handle.

Where scalability bites in the pipeline

The typical data science pipeline runs in three phases: Data engineering (wrangling → cleansing → preparation) → Machine learning (model learning ↔ model validation) → Operations (model deployment → data visualisation). Scalability concerns surface at two distinct points, and the lecture frames them as two separate questions:

QuestionWhere in the pipelineTool emphasised
How can we handle large amounts of incoming data?Data engineering / ingestionApache Spark (processing) · Apache Kafka (streaming ingestion)
How can we deploy our model so it handles large volumes of requests?Operations / servingDistributed / serverless deployment (cf. Lecture 9)

The key insight is that "scalability" is not one problem — scaling the data throughput (Spark/Kafka) is a different engineering challenge from scaling the serving layer (the request side).

Batch vs Stream processing

Batch processingStream processing
TimingData collected over a period, then processed once enough has accumulated / a time window passesData processed in (near) real-time; no waiting for a batch to fill
VolumeOften very large amounts processed at onceContinuous, smaller increments
ComplexitySimpler — a failed task can simply be retriedMore complex — the system must be fault tolerant so data is not lost mid-stream
Canonical toolApache SparkApache Kafka
Why is streaming "more complex"? In batch, if a job crashes you re-run it over the same stored chunk — the data is still sitting there. In a stream there is no convenient stored chunk to re-run; the system itself must guarantee (through acknowledgements, replication, and re-delivery) that an in-flight message is not lost when a consumer fails. Fault tolerance is therefore a design requirement of streaming, not an afterthought.

2. In-Memory Processing and Its Limits

Pandas stores a DataFrame in the RAM of a single machine. The most common criticism of pandas is that it does not work well for large amounts of data, because typical computers do not have the capacity to hold large DataFrames in memory.

What limits how much pandas can hold?

  • Available memory (RAM): pandas operates in memory, so the data it can handle is directly proportional to the system's RAM.
  • Data types: different dtypes consume different amounts of memory; this can be optimised in pandas (e.g., downcasting float64→float32, using category).
  • Complexity of operations: simple operations are less memory-intensive than complex ones (e.g., a large groupby), and system architecture itself affects how much memory is free for the operation.
Rule of thumb: on a 16 GB computer, pandas starts hitting performance issues at roughly ±1 million rows. This is a heuristic about memory pressure, not a hard limit — the real ceiling depends on dtypes and the operations you run.

Single-machine alternatives (still in-memory)

ToolIdeaWhat problem it solves
ModinDrop-in replacement for pandas (import modin.pandas as pd). Pandas is single-threaded; Modin scales pandas to use all CPU cores.Under-utilised cores on one machine (CPU-bound, not memory-bound)
PolarsA faster pandas replacement that has grown increasingly popular; built for speed on a single machine.Throughput on a single node
Apache SparkDistributes data and computation across many machines (a cluster).Data too large for any single machine's RAM
Key distinction to keep straight: Modin and Polars still run on a single machine — they make better use of that machine. Spark is fundamentally different: it spreads both the data and the work across a cluster, which is what lets it exceed any one machine's memory.

3. Apache Spark — Architecture

Spark is an engine for large-scale processing that supports both single-node machines and clusters of machines. It has become the de facto standard for big data processing. Its core property: it allows both computations and data to be divided across different machines (workers / nodes).

The three roles

ComponentWhat it isResponsibility
Driver nodeA single machine running the driver program, which holds the SparkSessionManages the Spark application: builds the logical plan, decides how work is split, sends instructions to workers, aggregates the final result
Cluster managerThe resource broker between driver and workersManages worker resources; assigns tasks to the available workers
Worker nodesMachines each running an Executor (with a Cache) that runs TasksDo the actual data processing on their partition; cache intermediate data; return results to the driver

Where the data lives

A Spark project typically starts with a dataset that resides in distributed storage — e.g., HDFS or AWS S3 — rather than on the driver's local disk. The motivating example in the lecture: a database of hundreds of millions of financial transactions from which you want to extract key statistics.

Mental model: the driver is the "brain" that plans and coordinates but does not hold the data; the workers are the "hands" that touch the data; the cluster manager is the "scheduler" that hands work to whichever hands are free. The local machine you type on is separate again — it sends requests to the driver.

4. The Spark Execution Walkthrough

The lecture walks a single query — group financial transactions by type and count them — through the full lifecycle.

from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("FirstSession").getOrCreate()
df = spark.read.parquet("data/financial_transactions.parquet")
print(df.groupby("type").count().show())

Step 1 — Establish a SparkSession

The SparkSession is the entry point to any Spark application. SparkSession.builder.getOrCreate() creates (or reuses) it; configurations can be specified here.

Step 2 — Link to the data (no data is read yet!)

When you call spark.read.parquet("s3://..."), the driver establishes a logical plan — it stores the location and the schema of the data. No actual data has been read, despite the method being named read. This is the single most counter-intuitive point in the lecture.

Step 3 — Perform an action

Calling an action (here show()) triggers the real work:

  1. The local machine sends a request to the driver, which already has a connection to the data.
  2. The driver sends each executor (assume 2 workers) specific instructions: (1) the operation(s) to perform and (2) information on the data partition — not the actual data.
  3. Workers obtain the partitions they need. In AWS S3, a parquet file is automatically divided into blocks (assume 6 blocks); the blocks are split among the workers (e.g., blocks 1–3 to worker 1, blocks 4–6 to worker 2).
  4. Each worker performs its action separately, producing partial results (Result 1, Result 2).
  5. The driver aggregates the workers' results and sends the final result back to the local machine.
All of partitioning, distribution, parallel execution, and aggregation is handled by Spark — the developer just writes DataFrame code. The output of the example was a small table of counts (e.g., credit 33371, transfer 33331, debit 33298) returned to the laptop.

5. Spark DataFrames

Spark DataFrames are similar to pandas DataFrames and expose built-in functions to make life easier for the developer — but they are designed for distributed, structured data.

What distinguishes a Spark DataFrame

  • Optimised for processing structured (tabular) data.
  • Built-in data-type protection through schema enforcement — the schema is known and enforced, which is also what lets Spark plan and optimise before touching data.
  • Named columns.
Example — largest transaction of Alice:
data = [("Alice",500),("Bob",300),("Alice",700),("Cathy",400),("Alice",200)]
columns = ["client","transaction"]
df = spark.createDataFrame(data, columns)

largest = (df.filter(df.client == "Alice")
     .agg({"transaction":"max"})
     .collect()[0][0])
Note that filter and agg build the plan; collect() is the action that actually executes it.

6. Lazy Evaluation

Because Spark can handle very large data, individual operations can take a long time. Spark therefore uses lazy evaluation: it does not perform any data operations until the results are actually used.

Worked example — total debit amount per date

StepCodeTypeEffect
1 Loaddf = spark.read.parquet(...)—Driver builds a logical representation (DF 1) holding the schema; Data: None
2 Filterdf_f = df.filter(df.type=="debit")TransformationLogical plan updated (DF 1 → DF 2). Operation is "performed" but never collected/shown; still no data loaded
3 Group + aggregatedf_g = df_f.groupby("date").sum("amount")TransformationPlan updated (DF 2 → DF 3 → DF 4). Plan now represents the full query; still no data loaded
4 Showdf_g.show()ActionTriggers execution: driver sends the logical plan + partition info to workers, workers obtain blocks, perform DF 1→DF 4, return results

Transformations vs Actions

TransformationsActions
Trigger execution?No — only the logical plan is updatedYes — execution of data operations
Examplesfilter, groupby, select, sum (within a plan)collect(), show(), count(), first(), take()

Why lazy evaluation is beneficial

  1. Prevents unnecessary operations from being performed → saves execution time.
  2. Allows more informed caching — Spark knows the whole plan before running it.
  3. Enables optimisations (see Catalyst, next section).
Exam trap: "the filter ran but nothing happened" is exactly the point. A transformation describes what you want; nothing is computed until an action demands a concrete result. This is why a script can chain ten transformations instantly and then "hang" on the first show().

7. Logical Plan Optimisation (Catalyst)

Spark does not simply execute the logical plan as the user wrote it. The Catalyst optimiser rewrites the plan using heuristics before execution. You can inspect this with explain(True), which prints both the Parsed Logical Plan and the Optimised Logical Plan.

Reading the plan

Logical plans are read bottom to top: the bottom is the Relation (the raw parquet source), and each line above is an operation applied to the result below it. In the lecture's example, the user wrote Selection → Grouping → Summing → Filtering (DF1→DF5), but the optimised plan moved the filter down next to the relation and added isnotnull(type).

== Optimised Logical Plan ==
Aggregate [type], [type, sum(amount) AS sum(amount)]
+- Project [type, amount]
  +- Filter (isnotnull(type) AND (type = "debit")) ← pushed DOWN, null check added
    +- Relation [...] parquet

Catalyst heuristics

HeuristicWhat it does
Predicate pushdownMoves filters as close to the data source as possible, reducing the amount of data read
Projection pushdownMoves SELECT operations close to the source, retrieving only the necessary columns
Constant foldingSimplifies constant expressions at compile time (e.g., 1 + 2 → 3)
Reordering joinsReorders joins to improve efficiency, especially in complex queries
Null eliminationEliminates unnecessary null checks based on data types
Join reordering / eliminationChanges a join's direction to reduce data transferred across partitions, and tries to remove unnecessary joins
Why "why?": filtering before grouping means far fewer rows enter the expensive aggregation, and pushing the filter to the source means fewer rows are ever read into memory. Lazy evaluation is what makes this legal — because nothing has executed yet, Catalyst is free to reorder the whole plan.

8. Parquet Format & Pushdown Optimisations

Parquet is a popular file format for PySpark and other big-data platforms because it is a columnar storage format: values of the same column are stored contiguously, rather than row by row.

What parquet stores beyond the data

  • The schema of the data.
  • Summary statistics — mean, max, min, number of missing, etc. — both for the entire dataset and per row group.

This metadata is precisely what enables the pushdown optimisations.

Predicate & projection pushdown with parquet

Whenever Spark does a filter (predicate) or a column selection (projection), it tries to push that operation down toward data loading, which can dramatically reduce data stored on disk or in memory.

Example — filtering on a category: For each row group, Spark reads the stored statistics first.
  • If the count of the wanted category in that row group is 0 → Spark never loads that row group into memory at all.
  • If the count is > 0 → Spark loads the row group, then applies the filter afterwards.
Projection pushdown is the columnar complement: because columns are stored separately, Spark can read only the columns the query needs and skip the rest entirely.
Connect the dots: columnar layout + per-row-group statistics is the physical mechanism; predicate/projection pushdown is the logical optimisation Catalyst chooses; lazy evaluation is what lets Catalyst plan it. The three layers reinforce each other.

9. Other Optimisations & Best Practices

Other optimisations (FYI)

  • Persistence and caching — keeping a reused intermediate DataFrame in worker memory (the Executor's Cache) so it is not recomputed. Lazy evaluation lets Spark cache more intelligently because it sees the whole plan.
  • Logical plan optimisation — the Catalyst rewriting covered above.

Pandas API on PySpark

The Pandas API on PySpark (pyspark.pandas) is a high-level API that closely mimics the functionality and interface of pandas. It works best with datasets that are larger than pandas can handle but not as large as typical big-data workloads.
  • Not as heavily optimised as the PySpark SQL API.
  • Does not (yet) have the same breadth of functions available.
  • When to use it: when you need a quick translation of an existing pandas workload and optimisation is not critical.
The scaling spectrum, ordered: pandas (single machine, single thread) → Modin / Polars (single machine, many cores) → Pandas-on-Spark (cluster, easy port, less optimised) → PySpark SQL API (cluster, fully optimised). Pick the leftmost tool that fits your data size and performance needs.

10. Apache Kafka

Apache Kafka is an open-source distributed event streaming platform. Where Spark is the canonical batch tool, Kafka is the canonical stream tool.

Messaging systems: batch vs stream

In a batch job, the consumer of the data (the processing engine) checks at predefined times whether new data is available and processes whatever is there. As we move toward real-time applications this polling becomes inefficient. In stream processing, consumers are notified when new data is available. The commonly used model is the publish-subscribe model:

Publisher → Input channel → Message Broker → Output channel → Subscriber(s)

The broker

The message broker:

  • Acts as an intermediary between producers and consumers of data.
  • Creates backlogs of data (queues).
  • Handles new subscriptions and producers, as well as failures.
  • Introduces asynchronous functionality (producers and consumers need not be active at the same time).
  • Allows load balancing.

Delivery patterns: load balancing vs fan-out

PatternHow messages are distributedUse case
Load balancingEach message goes to exactly one consumer (e.g., m1→Consumer 2, m2→Consumer 1, m3→Consumer 2…). Work is split across consumers.Parallelise heavy processing across a consumer group
Fan-outEvery consumer receives every message (all consumers see m1, m2, m3…).Independent subscribers each needing the full stream

Acknowledgements & fault tolerance

Consumers send an acknowledgement (ack) to the broker once a message is successfully processed. If a consumer crashes before acking (e.g., Consumer 2 takes m3, then crashes), the broker has not received the ack, so it re-delivers that message to another consumer (m3 is reassigned to Consumer 1). This is the concrete mechanism that makes streaming fault tolerant — and exactly the complexity that batch processing avoids by simply re-running a stored chunk.
Putting it together (wrap-up): Kafka ingests and buffers high-velocity event data reliably; Spark processes large data (batch or micro-batch) with lazy, Catalyst-optimised, pushdown-aware execution over distributed storage. Together they answer the two opening questions — handling large incoming data, and feeding scalable downstream analytics/serving.

Short Answer / Oral Exam — 10 Questions

Short Answer 1 · Spark execution lifecycle
Walk me through what happens, end to end, when you run spark.read.parquet(...).groupby("type").count().show() on a cluster. Be explicit about which component does what, and where the data is at each stage.
Model Answer:
  1. SparkSession / read: The driver's SparkSession registers the source. read.parquet only builds a logical plan — it records the location and schema. No data is read yet.
  2. Transformations: groupby("type").count() further updates the logical plan. Still nothing executes.
  3. Action (show()): This triggers execution. The local machine requests the result from the driver.
  4. Distribution: The driver, via the cluster manager, sends each executor the operations to perform and the partition information — not the data itself. The parquet file in S3 is split into blocks (e.g., 6 blocks across 2 workers).
  5. Parallel execution: Each worker reads only its partitions into its executor memory and computes a partial count (Result 1, Result 2).
  6. Aggregation: The driver combines the partial results into the global count table and returns it to the laptop.
Key emphasis: the driver plans and aggregates but never holds the bulk data; the workers touch the data; the cluster manager schedules; the data lives in distributed storage.

Likely follow-up questions:
  • Which steps were transformations and which was the action?
  • If you replaced show() with another transformation, would any data be read? (No.)
  • Why can't a single worker just compute the final count alone?
Short Answer 2 · Lazy evaluation
Define lazy evaluation. Distinguish transformations from actions with examples, and explain the three benefits. Why is filter() fundamentally different from show()?
Model Answer: Lazy evaluation means Spark performs no data operations until the results are actually needed. Transformations (filter, groupby, select, sum) only update the logical plan and trigger nothing. Actions (collect, show, count, first, take) trigger execution of the accumulated plan.

Three benefits: (1) prevents unnecessary operations, saving execution time; (2) allows more informed caching, since Spark sees the whole plan; (3) enables optimisations (Catalyst).

filter() describes what data you want and returns a new (still un-computed) DataFrame; show() is an action that forces Spark to actually read partitions and produce concrete output. That is why chaining transformations is instantaneous while the first action does the heavy lifting.

Likely follow-up questions:
  • Give an example where lazy evaluation saves work that an eager engine would have wasted.
  • If you call two actions on the same DataFrame, is the data read twice? How would caching change that?
  • Is count() a transformation or an action — and why does that matter for debugging timing?
Short Answer 3 · Catalyst & logical plans
A user writes selection → grouping → summing → filtering. After explain(True) the optimised plan has moved the filter down to the source and added an isnotnull check. Explain what happened and which heuristics were used. How do you read the plan?
Model Answer: Spark does not run the user's plan verbatim. The Catalyst optimiser rewrites it. explain(True) shows the parsed (user) plan and the optimised plan. Plans are read bottom to top: the bottom is the parquet Relation, and operations stack upward.

Catalyst applied predicate pushdown — moving the filter next to the relation so fewer rows are read and fewer rows enter the expensive aggregation. The added isnotnull(type) reflects null elimination / handling, removing rows that can't match before doing work. This rewrite is legal precisely because of lazy evaluation: nothing executed, so Spark could reorder the whole plan.

Other heuristics to mention: projection pushdown (read only needed columns), constant folding (1+2→3), reordering joins, join reordering/elimination.

Short Answer 4 · Parquet & pushdown
Explain why parquet is so well suited to Spark. Cover columnar storage, the metadata it keeps, and walk through the "filtering on a category" example to show how predicate pushdown actually avoids loading data.
Model Answer: Parquet is a columnar storage format: each column's values are stored together. It also stores metadata — the schema and summary statistics (min, max, mean, missing count) for the whole dataset and per row group.

Predicate pushdown example: filtering for a category, Spark first reads each row group's stored statistics. If the category's count in a row group is 0, Spark never loads that row group into memory. If the count is > 0, it loads the row group and applies the filter afterwards. Projection pushdown is the columnar complement: because columns are stored separately, Spark reads only the columns the query needs.

The payoff is far less data read from disk and held in memory — which is exactly the scaling bottleneck.

Short Answer 6 · Batch vs stream
Compare batch and stream processing across timing, complexity, and fault handling. Map each to its canonical tool, and explain precisely why streaming is the more complex paradigm.
Model Answer: Batch: data accumulates over time and is processed once a window passes or enough data is available; often very large volumes at once; canonical tool Spark. Failure handling is simple — re-run the task over the stored chunk.

Stream: data processed in (near) real-time with no waiting; consumers are notified as data arrives; canonical tool Kafka. It is more complex because the system must be fault tolerant — there is no convenient stored chunk to re-run, so the system itself must guarantee (via acks, queuing, re-delivery, replication) that in-flight data is not lost when a consumer fails.

Short Answer 7 · The broker & pub-sub
Describe the publish-subscribe model and the responsibilities of the message broker. Why does inserting a broker between producers and consumers improve a system's scalability and robustness?
Model Answer: In publish-subscribe, a publisher sends to an input channel → message broker → output channel → subscriber(s). The broker: acts as an intermediary between producers and consumers; creates queues/backlogs; handles new subscriptions, new producers, and failures; introduces asynchronous functionality; and allows load balancing.

Why it helps: the broker decouples producers from consumers. Producers don't need to know who consumes, how many consumers there are, or whether they're currently online — they just publish. The broker buffers messages (so a slow or temporarily offline consumer doesn't block producers), absorbs bursts, and lets you add/remove consumers freely. That decoupling is what makes the system scalable (add consumers for more throughput) and robust (failures are isolated and recoverable).

Likely follow-up questions:
  • What would break if producers wrote directly to consumers with no broker?
  • How does the queue help during a sudden burst of events?
  • How does the broker enable load balancing specifically?
Short Answer 8 · Delivery patterns & fault tolerance
Contrast load balancing and fan-out delivery. Then explain acknowledgements and walk through what happens when a consumer crashes mid-message. How does this deliver the fault tolerance streaming requires?
Model Answer: Load balancing: each message is delivered to exactly one consumer, splitting the workload across a consumer group (e.g., m1→C2, m2→C1, m3→C2…). Fan-out: every consumer receives every message — used when independent subscribers each need the full stream.

Acknowledgements: a consumer sends an ack once it has successfully processed a message; the broker then knows it can be considered done. Crash scenario: if Consumer 2 takes m3 and crashes before acking, the broker has no ack, so it re-delivers m3 to another consumer (e.g., Consumer 1). No message is lost.

This re-delivery on missing-ack is precisely the fault-tolerance machinery that makes streaming reliable — and the complexity that batch sidesteps by simply re-running a stored chunk.

Likely follow-up questions:
  • Could a message be processed twice under this scheme? What does that imply for consumer design (idempotency)?
  • When would you choose fan-out over load balancing in a data pipeline?
  • How does this connect back to "streaming is more complex than batch"?
Short Answer 9 · Why Spark scales
A student asks: "If pandas just runs out of RAM, why doesn't Spark?" Give a complete, architecturally grounded answer.
Model Answer: pandas is in-memory and single-machine: the DataFrame must fit in one computer's RAM, so its capacity is bounded by that machine. Spark is fundamentally different — it distributes both data and computation across a cluster. The driver plans the work and coordinates but holds no bulk data; the cluster manager schedules; the workers each load and process only their partition of the data in their own executor memory and caches.

So the dataset never needs to fit in any single machine; it is split into blocks (in distributed storage like HDFS/S3) and processed in parallel. Add lazy evaluation, Catalyst optimisation, and parquet pushdown, and Spark also reads far less data than a naïve scan would. That combination — horizontal distribution plus read-minimisation — is why Spark scales where pandas cannot.

Short Answer 10 · End-to-end design
Design a scalable pipeline: hundreds of millions of financial transactions stream in continuously, and the business wants daily total debit amounts per date, exposed to downstream consumers. Name the tools, justify each choice, explain how lazy evaluation and pushdown help, and note what makes it production-ready.
Model Answer:
StageToolJustification
IngestionKafkaTransactions arrive as a high-velocity event stream; the broker decouples producers from consumers, buffers bursts in queues, and provides fault tolerance via acks/re-delivery so no event is lost.
StorageS3/HDFS in parquetDistributed storage holds data far beyond one machine; columnar parquet + per-row-group stats enable predicate & projection pushdown.
ProcessingSpark (PySpark SQL API)Distributes data & computation across workers. The query filter(type=="debit").groupby("date").sum("amount") is built as transformations; show()/write is the action.
ServingScalable deployment (cf. Lecture 9 — e.g., serverless/API layer)To handle large volumes of downstream requests for the computed aggregates.
How lazy evaluation + pushdown help: Spark builds the full plan before executing, so Catalyst pushes the debit filter down to the parquet source (skipping row groups with no debits) and reads only the type, date, and amount columns. Far less data is read and far fewer rows reach the aggregation.

Production-readiness: partition the parquet by date for pruning; cache reused intermediates; monitor the Kafka consumer lag; make consumers idempotent (messages can be re-delivered); schedule the daily batch (or use micro-batch/structured streaming); add alerting and schema validation.
