1. Version Control

What is Version Control? A system that tracks changes made to files over time, allowing users to keep a full history, enable collaborative editing without overwrites, and revert to prior states.

The Problem Without It

In a team project, each member working on their own .zip copy leads to:

  • Manual merging of changes — error-prone at line-by-line level
  • Divergent virtual environments (mismatched package versions)
  • Massive duplicate storage across thousands of versions
  • Inability to cleanly revert to a stable state

Key insight: Version Control Systems (VCS) do not store a full copy of the repo for every change — they store only the diffs (changes). For the user the result is equivalent, but storage is far more efficient.

Local vs Remote Repository

TermDefinitionExample
Remote repoProject hosted on the internetGitHub, GitLab, Bitbucket
Local repoProject copy on your machine, with hidden .git folder~/Documents/myproject
Working directoryActual files you edit — distinct from the local repo until staged+committedAny unsaved/uncommitted change
The .git folder is hidden by default. On Windows, enable hidden items; on Mac use Cmd+Shift+.

2. Using Git(hub) — Core Workflow

Starting a Repository

ApproachCommandWhen to use
Clone from remotegit clone <url.git>Remote repo already exists
Init locallygit initStart tracking an existing local folder

Keeping Local Repo Up-to-Date (Remote → Local)

git fetch origin main  →  downloads remote history (read-only view)
git diff origin/main   →  inspect differences
git merge             →  apply changes to local
git pull             →  fetch + merge in one step
origin is the shorthand alias for the URL of the remote repository from which you originally cloned.

The Photo Album Analogy (Local → Remote)

Think of .git as a photo album. Git does not record in real-time — you decide when to "take a photo":
  1. Staging — choose which files to include: git add <file> or git add .
  2. Committing — take the snapshot: git commit -m "Descriptive message"
  3. Pushing — add it to the remote album: git push origin main
Changes in your working directory are NOT in your local repo until you add and commit. Git only tracks files that have been staged or already exist in the repository.

3. Undoing Changes

SituationCommandEffect
Uncommitted change in working dirgit restore <file> or git checkout <file>Reverts file to last committed state
Undo last commit (not pushed)git reset --soft HEAD~Undoes commit, keeps changes staged
Roll back to older commit (not pushed)git reset <HEAD>Unstages all post-commit changes (keeps in working dir)
Roll back completely (wipe)git reset --hard <HEAD>Discards all changes after target commit
Undo a pushed commit safelygit revertCreates a new commit that undoes the target commit
--soft vs --mixed vs --hard:
  • --soft: moves HEAD, leaves changes staged
  • --mixed (default): moves HEAD, unstages changes (left in working dir)
  • --hard: moves HEAD, discards all changes entirely
Git only tracks changes in files that have been staged or are already in the repository. Untracked new files are invisible to Git unless you git add them first.

4. Branches

Branches are independent copies of the repository where changes don't affect other branches. They are essential for writing experimental or potentially unstable code without endangering the production (main) branch.

Why Branches?

Common production setup: main/master → testing → dev. If a bug fix is applied directly to main and turns out to be wrong, it can crash production. Branches isolate risk.

Reverting a bad push is not enough if other collaborators have already git pulled the broken code. Branches prevent this entirely.

Branch Commands

git branch <name>               → create branch
git checkout <name>            → switch to branch
git checkout -b <name>         → create + switch
git push origin <name>         → publish branch to remote
git merge <branch_WU>          → merge updates into current branch
git branch -d <name>           → delete branch locally
Workflow rule: Always create the branch BEFORE making changes. Make changes AFTER switching to the new branch, or the edits will land on the wrong branch.

Merge Conflicts

Conflicts occur when two branches modify the same line in a file, or one branch edits a file the other branch deleted. Git cannot auto-resolve these — human decision is required:

# Keep a file in conflict:
git add <file>

# Remove a file in conflict:
git rm <file>

Forking vs Branching vs Cloning

OperationOwnershipUse case
CloneSame repoGet a local copy of a repo you have access to
BranchSame repoIsolated development within the same project
ForkYour copy, disconnectedContribute to a public repo you don't own; propose fixes via pull request

Git Stash

git stash saves all uncommitted tracked changes and resets your working directory, without committing. Useful when you realize you're on the wrong branch or need to switch context mid-work.

git stash pop — re-applies the stashed changes.

5. Important Extras

requirements.txt

Ensures all collaborators use the same Python package versions.
pip freeze > requirements.txt (or pip list --format=freeze > requirements.txt for cleaner output)
Always keep it updated and committed. Git hooks can be used to automatically abort a commit if the file is outdated.

.gitignore

A file containing rules that tell Git which files/folders to ignore (not track). Common exclusions: .log, .temp, files with passwords/API keys, large binary files, virtual environment folders. The .gitignore file itself is tracked — it contains rules, not the ignored content.

GitHub Pages

A special GitHub repository feature that serves HTML/CSS/JS as a hosted website. Useful for portfolios, documentation, and simple tools.

Pull Requests (PR)

After forking a repo and fixing a bug, you can submit a pull request to notify the original repo owner to review and merge your fix. Many organizations also use PRs as a formal review gate for branch merges.

Security warning: Never blindly clone/fork/install GitHub repos, especially low-traffic packages. Malicious actors have embedded trojan horses in repos. Always check stars, issues, and update history.

6. Hugging Face 🤗

Hugging Face is the central platform for open-source ML. It hosts 900,000+ datasets and 2,700,000+ models, along with documentation, playgrounds (Spaces), and a simple Python API (transformers).

Model Card

Each model on Hugging Face has a Model Card (a README-style document) that typically contains:

  • Performance benchmarks
  • Number of parameters (≈ model size)
  • Training information (data, method)
  • Known biases and limitations

The Pipeline API

The pipeline() function from the transformers library encapsulates all preprocessing, model inference, and post-processing steps. You specify only the task and optionally the model — the API handles everything else.
from transformers import pipeline

# Sentiment Analysis
classifier = pipeline("sentiment-analysis")
classifier("I love this course!")

# Translation (Dutch → English)
translator = pipeline("translation", model="Helsinki-NLP/opus-mt-nl-en")
translator("Hallo, ik ben Thomas.")

Pipeline Task Types

TaskDescriptionExample
Sentiment AnalysisClassify text as POSITIVE/NEGATIVEProduct reviews, social media
TranslationConvert between languagesopus-mt-nl-en (Dutch → English)
Zero-Shot ClassificationPredict user-defined labels not in training dataClassify text into custom categories
Named Entity Recognition (NER)Tag tokens as person, org, location, date, etc.Extract entities from documents
Question AnsweringExtract answer from a given context passageDocument Q&A
SummarizationCondense text to shorter formPreprocessing or standalone summarizer
Models are downloaded to your local machine (stored in .cache). Always verify you have sufficient disk space before downloading. Large Language Models (LLMs) can be several gigabytes. Models are only downloaded once.
Zero-Shot Classification is a form of transfer learning where the model predicts labels it has never seen during training. This makes it extremely flexible but potentially less accurate than a fine-tuned classifier.

Files & Versions Tab

Each model on Hugging Face has a Git-based repository (Files & Versions tab). This allows you to inspect model weights, config files, and the full version history — the same infrastructure as GitHub.

Beyond the Pipeline: Ollama

For Large Language Models specifically, Ollama allows you to run LLMs locally from your terminal or Python code. LLMs handle more complex reasoning but are larger in size.

Combining tools: Hugging Face models + LangChain + custom pipelines = powerful end-to-end NLP systems. This is the current industry direction for production ML applications.
