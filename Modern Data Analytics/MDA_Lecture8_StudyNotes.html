1. What is Docker & Why Does It Matter?

Docker is a container-based platform for developing, shipping, and running applications inside lightweight, isolated environments called containers. It solves the classic "works on my machine" problem by packaging code together with all its dependencies.

The Core Problem

A data scientist trains a model locally, shares the code, and teammates cannot reproduce the results — different OS versions, library mismatches, missing environment variables, etc. Docker solves this by bundling everything needed into a single portable unit.

Lunchbox analogy: A container is like a sealed lunchbox. You pack your meal (code + dependencies) inside. No matter which kitchen (Windows, Mac, Linux) you open it in, the contents are the same.

Benefits for Data Science

BenefitWhat it means in practice
ReproducibilityIdentical environment every time — replicating ML experiments across machines
PortabilityRun the same container on a laptop, a server, or the cloud without changes
ScalabilityLightweight containers can be spun up or torn down quickly to match demand
CollaborationShare a Docker image instead of lengthy "setup" instructions

Container vs. Virtual Machine

A VM virtualises an entire OS (heavy — GBs, slow boot). A container shares the host OS kernel and only packages the application layer (lightweight — MBs, starts in seconds). Containers are faster and cheaper to run, but share the host kernel so they are less isolated than VMs.

3. Writing a Dockerfile

A Dockerfile is a plain-text script Docker reads top-to-bottom. Each instruction creates a new read-only layer in the image.

Core Instructions

InstructionPurposeExample
FROMDeclare base image (must be first)FROM python:3.9
WORKDIRSet working directory for subsequent commandsWORKDIR /app
COPY <src> <dest>Copy files from host into imageCOPY requirements.txt /tmp
RUNExecute a shell command during build; result is committed as a new layerRUN pip install -r /tmp/requirements.txt
ENVSet environment variablesENV DEBUG=false
EXPOSEDocument which port the app listens on (does not actually open it)EXPOSE 8888
CMDDefault command run when container starts; only the last CMD takes effectCMD ["python", "app.py"]
Minimal data science Dockerfile:
FROM python:3.9
COPY requirements.txt /tmp
RUN pip install -r /tmp/requirements.txt
Running docker build . -t docker-for-ds:1.0.0 creates the image. Then docker run docker-for-ds:1.0.0 python --version confirms Python 3.9 is available.

Layer Caching

Docker caches each layer. If a layer's instruction and its inputs haven't changed, Docker reuses the cached layer — dramatically speeding up rebuilds. This is why it's best practice to copy requirements.txt and run pip install before copying the rest of the source code: dependency layers rarely change and stay cached.

Image Layers (Read-Only) vs Container Layer (Read-Write)

An image is a stack of read-only layers (one per Dockerfile instruction). When you docker run an image, Docker adds a thin writable container layer on top. All runtime file writes go there. When the container is deleted, this layer is lost.

Key exam point: EXPOSE is documentation only — it does NOT open a port on the host. To actually make a port accessible you must publish it at runtime with -p <host-port>:<container-port>.

VS Code Docker Extension Shortcut

Instead of writing a Dockerfile manually, use Ctrl+Shift+P → Docker: Add Docker Files to Workspace. VS Code prompts for platform (Python, Node.js, etc.) and port, then auto-generates a valid Dockerfile and optional Compose file.

4. Storing and Sharing Data

By default, data written inside a container lives only in its writable container layer and is lost when the container is removed. To persist data, store it outside this layer using a mount.

The Three Mount Types

TypeWhere data livesManaged byBest use case
VolumeDocker-managed area on host filesystem (/var/lib/docker/volumes/)DockerPersistent data across container restarts; sharing data between containers
Bind mountAny path on the host filesystemHost OSLocal dev — edit code on host, test inside container simultaneously
tmpfs mountHost RAM only (never touches disk)Host kernelSensitive/temporary data; fast in-memory scratch space

Volumes in Practice

# Create
docker volume create my-vol

# Mount when running a container
docker run -d -v my-vol:/app/data my-image

# Inspect
docker volume inspect my-vol

# List / Remove
docker volume ls
docker volume rm my-vol
Volumes vs. Bind mounts isolation: Volumes are fully managed and isolated by Docker — the host OS can't easily interfere. Bind mounts expose the host path directly; both host processes and container processes can write simultaneously, which is useful for development but less safe in production.

Bind Mounts in Practice

# ${PWD} = current working directory on the host
docker run -v ${PWD}:/app/data my-image

tmpfs Mounts in Practice

docker run --tmpfs /app/logs my-image

Everything written to /app/logs is stored in RAM. It disappears when the container stops — ideal for credentials, session tokens, or intermediate ML results that should never touch disk.

tmpfs mounts are only available on Linux hosts. On Docker Desktop for Windows/Mac they are silently ignored or emulated.

5. Docker Networking

Each container runs in isolation. Without networking, containers cannot communicate with each other or the outside world. Docker networking provides the "wiring" between containers and the external network.

House analogy: Containers are rooms; the Docker host is the house. Network types define what kind of hallways and doors connect the rooms.

Network Types Compared

TypeIsolationTypical useSyntax highlight
Bridge (default)Private virtual network on a single host; containers can communicate by name on same bridgeLocal multi-container apps; most commondocker run --network my-bridge ...
HostNo isolation — container shares host IP & ports directlyMaximum performance; avoid in productiondocker run --network host ...
NoneComplete isolation — no network access at allSecurity-critical offline processingdocker run --network none ...
OverlayCross-host private network (Docker Swarm)Production clusters spanning multiple machinesConfigured via Docker Swarm / Compose

Publishing Ports (Bridge Network)

# Syntax: -p <host-port>:<container-port>
docker run -p 8888:80 my-image

This opens port 8888 on the host; requests to localhost:8888 are forwarded to port 80 inside the container. Without -p, no traffic from outside can reach the container even on a bridge network.

On a custom bridge network (as opposed to the default bridge), containers can resolve each other by container name (DNS). On the default bridge, they can only communicate by IP address.

Creating a Custom Bridge Network

docker network create my-bridge
docker run -d --name jupyter --network my-bridge jupyter/base-notebook
docker run -d --name db --network my-bridge postgres
# jupyter can now reach postgres at hostname "db"
The default bridge network is created automatically when Docker is installed. However, it does not support DNS-based container name resolution — that is only available on user-defined bridge networks.

6. Docker Compose — Managing Multi-Container Apps

Docker Compose lets you define an entire multi-container application in a single docker-compose.yml file and launch everything with one command: docker-compose up.

Why Compose?

As a project grows (Jupyter + database + backend API), manually running long docker run commands becomes error-prone. Compose declaratively describes every service, its image, ports, volumes, environment variables, and dependencies.

Core Compose Commands

CommandEffect
docker-compose upBuild (if needed) and start all services
docker-compose up -dStart in detached (background) mode
docker-compose downStop and remove all containers defined in the file
docker-compose buildRe-build images without starting containers
docker-compose logsStream logs from all services

Example: Jupyter + PostgreSQL

version: '3'
services:
  jupyter:
    build: .
    ports:
      - "8888:8888"
    volumes:
      - ./notebooks:/home/jovyan/work
    depends_on:
      - db
  db:
    image: postgres
    restart: always
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: mydb
    ports:
      - "5432:5432"
depends_on controls start order only — it does not wait for the database to be fully ready before starting the dependent service. For true readiness checks, healthchecks or tools like wait-for-it are needed.

Compose Benefits

  • Reproducibility — the same YAML produces identical setups anywhere
  • Collaboration — new team members run one command to get started
  • Scalability — easily add more services without rewriting infra
Docker Compose creates services on a shared default network automatically, so containers within the same Compose file can reach each other by service name without explicit network configuration.

7. Introduction to Kubernetes

Kubernetes (K8s) is a container orchestration system that manages containers across multiple machines (hosts). While Docker Compose handles multi-container apps on a single host, Kubernetes scales this to hundreds of machines in production.

Docker Compose vs Kubernetes

FeatureDocker ComposeKubernetes
ScaleSingle machineMulti-machine, production-ready
ComplexitySimple, easy to set upComplex but powerful
Use caseLocal dev & testingProduction, large-scale systems
ConfigurationOne YAML fileMany YAML files (pods, services, etc.)
Self-healingNo automatic recoveryAutomatically restarts crashed containers
EcosystemBasic networking & volumesFull orchestration: load balancing, autoscaling

When Kubernetes Shines

  • You need to run hundreds of containers across many servers
  • Automatic restart of crashed containers (self-healing)
  • Rolling updates with zero downtime
  • Automatic scaling (scale up under load, scale down when idle)
  • Load balancing across container replicas
Mental model: Docker Compose = recipe for building a meal at home. Kubernetes = industrial kitchen management system for a chain of restaurants. Docker is the runtime; Kubernetes is the orchestrator that decides where, when, and how many Docker containers to run.
Practical note: Setting up Kubernetes from scratch is non-trivial. In practice, managed services (Google GKE, Amazon EKS, Azure AKS) abstract away much of the complexity. For the exam, focus on the conceptual differences between Compose and Kubernetes.

Short Answer — 10 Questions (Oral Exam Style)

Short Answer 1 · Architecture
Explain the difference between a Docker Image and a Docker Container. What is the role of the writable container layer, and what happens to it when the container is stopped and removed?
Model Answer: A Docker Image is a read-only, layered template created from a Dockerfile. It is static and can be stored in a registry. A Docker Container is a running instance of an image — it adds a thin, writable container layer on top of the image's read-only layers. Any files written at runtime (logs, model outputs, etc.) go into this writable layer, which is unique to that container instance. When the container is stopped, the writable layer is preserved on disk (the container still exists as a stopped object). When the container is removed (docker rm), the writable layer is permanently deleted — all data written inside the container that was not persisted via a volume or bind mount is lost.

Likely follow-up questions:
  • How would you preserve data written inside a container across restarts?
  • Why is it a bad idea to store production database files in a container's writable layer?
  • Can multiple containers run from the same image simultaneously? What do they share?
Short Answer 2 · Dockerfile Design
Walk through the purpose of each instruction in the following Dockerfile and explain the rationale for the ordering chosen:

FROM python:3.9  / COPY requirements.txt /tmp  / RUN pip install -r /tmp/requirements.txt  / WORKDIR /app  / COPY . .  / CMD ["python", "main.py"]
Model Answer:
  • FROM python:3.9 — declares the base image (official Python 3.9). Must be the first instruction; it forms the foundation layer.
  • COPY requirements.txt /tmp — copies only the dependency file into the image. Doing this before copying all source code exploits Docker's layer cache: if requirements.txt hasn't changed, the next layer is reused.
  • RUN pip install -r /tmp/requirements.txt — installs dependencies as a committed read-only layer. Because it follows only the requirements copy, it is cached as long as requirements don't change, even if app code changes.
  • WORKDIR /app — sets the default working directory for all subsequent instructions and for the container's runtime shell.
  • COPY . . — copies the rest of the application source code. Placed after dependency installation so code changes don't invalidate the expensive pip install layer.
  • CMD ["python", "main.py"] — sets the default command to run on container start. Only the last CMD in a Dockerfile takes effect.
Likely follow-up questions:
  • What would happen if you put COPY . . before the pip install step in terms of caching?
  • What is the difference between CMD and RUN?
  • How would you override the CMD at runtime without modifying the Dockerfile?
Short Answer 3 · Storage
Compare Docker Volumes, Bind Mounts, and tmpfs Mounts. For each, describe the use case where it is the most appropriate choice in a data science context.
Model Answer:
Docker Volume: Managed entirely by Docker in a Docker-reserved area of the host filesystem. Data persists independently of the container lifecycle. Best for: storing trained model weights, databases (PostgreSQL data directory), or any data that must survive container restarts and be shared across multiple containers.

Bind Mount: Maps a specific host directory directly into the container. Both host and container can read/write simultaneously. Best for: local development — editing Jupyter notebooks or Python scripts on the host while the container immediately sees the changes without rebuilding.

tmpfs Mount: Stores files exclusively in host RAM; never written to disk; data lost when the container stops. Best for: sensitive data (API keys, credentials) that must not be logged or persisted, or for fast temporary scratch space (intermediate ML computations).

Likely follow-up questions:
  • What are the security implications of using a bind mount vs. a volume in production?
  • Can two containers share the same Docker volume? What are the concurrency risks?
  • Why might you choose a tmpfs mount over simply storing credentials as environment variables?
Short Answer 4 · Networking
Describe Docker's four main network types (bridge, host, none, overlay). For each, state whether containers get network isolation and in which scenario a data scientist might use it.
Model Answer:
Bridge (default): Creates a private virtual network on the host. Containers are isolated from each other and the external network by default, but can communicate within the same bridge and be exposed externally via port publishing (-p). User-defined bridge networks additionally support DNS name resolution between containers. Data science use: connecting a Jupyter container to a database container on the same machine.

Host: The container shares the host's network interface directly — no virtual network layer. Fastest performance but no network isolation. Data science use: high-throughput data ingestion pipelines on Linux where the overhead of virtual networking is measurable.

None: Container has no network interfaces whatsoever. Completely isolated. Data science use: running a sensitive offline ML training job on private data that must have no outbound connectivity.

Overlay: Creates a virtual network spanning multiple Docker hosts, used with Docker Swarm. Data science use: distributed training or serving pipelines across a cluster of machines.

Likely follow-up questions:
  • Why does the default bridge network not support container name DNS resolution, while a user-defined bridge does?
  • If you use the host network on Windows or macOS Docker Desktop, what happens?
  • How would you verify which network a running container is attached to?
Short Answer 5 · Docker Compose
Explain the purpose of the depends_on field in Docker Compose. What does it guarantee, and what important limitation does it have? How can this limitation be addressed?
Model Answer: depends_on declares a startup ordering dependency between Compose services. For example, depends_on: [db] on the jupyter service tells Compose to start the db container before the jupyter container.

Limitation: It only guarantees that the db container has started, not that it is ready to accept connections. A PostgreSQL container may take several seconds after its process starts before it is actually ready to accept queries. If the Jupyter service attempts to connect during that window, it will fail.

Solution: Use health checks (healthcheck in the Compose file) combined with condition: service_healthy in the depends_on block (available in Compose v3.4+). Alternatively, use external tools like wait-for-it.sh or application-level retry logic.

Likely follow-up questions:

  • How would you scale a specific service to 3 replicas in Docker Compose?
  • If you change the Dockerfile but run docker-compose up without --build, will the image be rebuilt?
Short Answer 6 · Layer Caching & Build Optimisation
Explain Docker's layer caching mechanism. How does the order of Dockerfile instructions affect build performance, and what are the practical consequences of a poorly ordered Dockerfile in a team that rebuilds images frequently?
Model Answer: Each Dockerfile instruction creates a read-only layer. Docker caches each layer keyed by the instruction and its inputs. On a subsequent docker build, if a layer's instruction and its inputs are identical to the cached version, Docker reuses the cached layer and does not re-execute it. However, once any layer is invalidated (i.e., its inputs change), all subsequent layers must be rebuilt too — they cannot be reused.

Practical consequences of bad ordering: If COPY . . (all source code) appears before RUN pip install, then every trivial code change — fixing a typo, renaming a variable — invalidates the COPY layer, forcing pip install to re-run from scratch. In a team rebuilding multiple times per day, this wastes minutes per build and can slow the development cycle significantly.

Best practice: Place the slowest, least frequently changing steps (base image pull, dependency installation) early, and the most frequently changing steps (application code copy) late.

Likely follow-up questions:
  • How can you force Docker to ignore the cache for a specific build?
  • What is a multi-stage build and how does it help reduce final image size?
  • If you add a new Python library to requirements.txt, which layers are invalidated?

Short Answer 8 · Reproducibility in ML
A data scientist claims that "using Docker guarantees full reproducibility of ML experiments." Do you agree? What does Docker solve, and what reproducibility challenges remain even when using Docker?
Model Answer: Docker solves a significant subset of reproducibility issues — it eliminates environment-level variance by fixing the OS, Python version, library versions, system dependencies, and configuration. This is a major improvement over sharing only code and requirements files.

However, Docker alone does not guarantee full ML reproducibility:
  • Random seeds: If not set explicitly, operations involving randomness (weight initialisation, data shuffling, dropout) produce different results each run.
  • Data versioning: Docker packages code, not data. If the training dataset changes (new records, preprocessing updates), results differ.
  • Hardware non-determinism: GPU floating-point operations can be non-deterministic across different GPU models or driver versions, even with fixed seeds.
  • External dependencies: API calls, database queries, or network-fetched data inside the container can return different results over time.
  • Build-time vs. runtime: FROM python:3.9 without pinning to a specific digest may resolve to a different base image over time.
Likely follow-up questions:
  • How would you pin a Docker base image to ensure the exact same image is always used?
  • What tools complement Docker for full ML reproducibility? (e.g., MLflow, DVC, seeds)
  • Is it sufficient to use the same image on different hardware to guarantee identical results?
Short Answer 9 · Kubernetes vs. Docker Compose
Explain when a data science team should transition from Docker Compose to Kubernetes. What specific operational challenges trigger this transition, and what is the main trade-off?
Model Answer: Docker Compose is appropriate when all services fit on a single machine and the team primarily needs local development or simple single-host deployment. The transition to Kubernetes is triggered by:

  • Scale: The workload outgrows a single machine and must be distributed across multiple servers (e.g., a model serving API receiving thousands of requests per second).
  • High availability: The application must survive machine failures. Docker Compose has no self-healing; Kubernetes automatically restarts failed containers and reschedules them on healthy nodes.
  • Auto-scaling: Traffic patterns are variable. Kubernetes can automatically spin up more container replicas under load and scale down when demand drops.
  • Rolling deployments: The team needs zero-downtime updates — Kubernetes supports rolling updates and rollback strategies.
  • Resource management: In a shared cluster, Kubernetes enforces CPU/memory limits and schedules containers onto nodes with available resources.
Main trade-off: Kubernetes has significant operational complexity — it requires understanding pods, deployments, services, ingress controllers, and more. Setup and maintenance are non-trivial. Managed cloud services (GKE, EKS, AKS) reduce this burden.

Likely follow-up questions:
  • What is a Kubernetes Pod, and how does it relate to a Docker container?
  • Can Docker Compose files be converted to Kubernetes manifests? What tools exist for this?
  • What does "self-healing" mean concretely in Kubernetes?
Short Answer 10 · Design Scenario
Design a Dockerised data science environment for a team working on a customer churn prediction model. The environment needs: a Jupyter notebook server with scikit-learn and XGBoost, a PostgreSQL database for raw data, and persistence of notebooks and database data between sessions. Sketch the Docker Compose structure and justify your design choices.
Model Answer — Proposed Structure:
version: '3'
services:
  notebook:
    build: . # Dockerfile based on jupyter/scipy-notebook
    ports: ["8888:8888"]
    volumes:
      - ./notebooks:/home/jovyan/work # bind mount
    depends_on: [db]
    environment:
      DB_HOST: db
  db:
    image: postgres:15
    restart: always
    volumes:
      - pg_data:/var/lib/postgresql/data # named volume
    environment:
      POSTGRES_USER: analyst
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: churn
volumes:
  pg_data:
Design justifications:
  • Notebook bind mount (./notebooks:/home/jovyan/work): allows analysts to use their host editor (VS Code, etc.) to edit notebooks while they run inside the container. Changes are immediately reflected.
  • Named volume for PostgreSQL (pg_data): database files are managed by Docker, persisting across container removals. A bind mount would work but volumes are preferred for database data as Docker manages permissions correctly.
  • Service name as hostname: by using DB_HOST: db, the notebook can connect to PostgreSQL at hostname db — Compose's built-in DNS handles resolution.
  • restart: always on db: ensures the database comes back automatically if it crashes, without requiring developer intervention.
  • depends_on: guarantees the database container starts before the notebook. (Would add healthcheck for production.)
Likely follow-up questions:
