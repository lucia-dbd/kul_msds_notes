1. In-Memory Analytics & The Data Landscape

Core assumption of most data science tools: the dataset fits in RAM. Servers with 512 GB of RAM have become relatively cheap — often cheaper than running a full HDFS cluster, particularly in cloud environments. This covers a surprisingly large range of real-world problems.

Two Sides of the Modern Data Stack

Infrastructure SideAnalytics & ML Side
Big Data storage & integrationData Science & Machine Learning
Architecture, NoSQL & NewSQLAI, NLP, Computer Vision
Streaming & real-time pipelinesBusiness Intelligence & Visualization
AI/ML Ops, CI/CD for modelsStatistical modelling & analytics

The Spectrum: In-Memory → On-Disk → Distributed

TierWhen to useTools
In-memoryData fits in RAM (most cases!)pandas, Polars, R data.table, DuckDB
On-disk / intermediateData exceeds RAM but single machineDask, Vaex, disk.frame, DuckDB, Polars
On-GPUMassive parallelisable linear algebraCUDA, JAX, PyTorch, CuDF (RAPIDS)
Distributed (big data)Truly petabyte-scale, multi-machineSpark, Hadoop, cloud warehouses
⚠ "Pandas is crashing because I'm trying to work with a 50GB dataset" is not a good reason to jump straight to Spark. Most organisations that went full Hadoop/Spark would have been better served by better in-memory techniques, Polars, or DuckDB. Assess before committing.

On-Disk Intermediate Solutions

Tools like Dask, Polars, DuckDB, and Vaex use Directed Acyclic Graph (DAG) execution plans and column-oriented data structures to process datasets larger than RAM on a single machine — the same DAG principle later "rediscovered" by Spark.
Dask mirrors the Pandas API:
df = dd.read_csv('2015-*-*.csv') — lazy, partitioned reads.
df.groupby(df.user_id).value.mean().compute() — triggers execution.

2. Python & R Ecosystems for Analytics

Why Python and R?

The languages themselves are not what matter — it's their ecosystems. Python is described as "the second best language for everything." Both languages succeed because of the enormous library support built by their communities, not intrinsic language properties.

4. Data File Formats

Key Dimensions When Choosing a Format

  • Read speed vs. write (serialisation) speed
  • File size / compression efficiency
  • Row-oriented vs. column-oriented storage
  • Schema evolution support (can columns be added/renamed?)
  • Splittable for distributed processing
  • Human readability

Format Comparison

FormatOrientationSchema Evol.Best ForWeakness
CSV / JSONRow (text)PoorExchange, debuggingBulky, slow to query, no typing
Apache AVRORow (binary)ExcellentETL, data pipelines, streaming (Kafka)Not columnar — slow for analytics reads
Apache ParquetColumn (binary)GoodAnalytics, data lakes, ML feature storesNot ideal for frequent row-level updates
Apache Arrow / FeatherColumn (in-memory spec)GoodFast in-process exchange between R & PythonNot a persistent archival format
HDF5HierarchicalComplexScientific data, deep learning model weightsVery complex spec; overkill for tabular data
ORCRow+Column hybridGoodHive / Hadoop ecosystemsDeclining usage; largely replaced by Parquet
SQLiteRow (relational)Via ALTEREmbedded, multi-table, SQL queriesOperational OLTP focus; less suited to analytics
Practical recommendation: Use Parquet or Feather/Arrow as primary formats. AVRO for write-heavy ETL and Kafka integration. Many organisations adopt a hybrid — AVRO for ingestion/streaming, Parquet for the analytical layer.
Apache Arrow is not a file format — it is a columnar in-memory representation specification. Its layout is designed to be highly cache-efficient for analytics and enables zero-copy data interchange between systems (Python ↔ R, Spark ↔ pandas) without serialisation overhead. Feather is Arrow on disk.

Version Control with Git

Git (created by Linus Torvalds in 2005 for the Linux kernel) is the universal standard for source code versioning. Every directory is a full-fledged repository with complete history. GitHub / GitLab host remote repositories. Good practice even for a "team of one." Recruiters routinely review GitHub profiles to assess practical experience.

AutoML

AutoML tools (Auto-sklearn, H2O AutoML, TPOT, AutoGluon, FLAML, etc.) automate the search through algorithm + hyperparameter space. The hardest component is the hyperparameter search procedure over a vast combinatorial space. May also incorporate automated feature engineering (FeatureTools, AutoFeat). Increasingly superseded by LLM-based approaches.

Data Labelling

  • Manual labelling is expensive and slow — tools like Labelbox, imglab, and make-sense provide efficient UIs.
  • Active learning speeds labelling: train a model → query its most uncertain predictions → label those next.
  • Weak supervision (Snorkel): programmatic labelling with noisy heuristics ("labelling functions") combined by a generative model — avoids labelling every example manually.
  • Foundation models (SAM — Segment Anything; LLMs) are now widely used to pre-label data, dramatically reducing human effort.

6. Model Deployment & MLOps

In real-world ML systems, only a small fraction of code is actual ML. The vast infrastructure surrounding it — data pipelines, serving, monitoring, governance — represents enormous hidden technical debt (Sculley et al., 2015).

Five Categories of Deployment Issues

CategoryCore problemKey principle
Data lineageTraining data sources are dispersed; preprocessing steps not trackedUnified data layer; all preprocessing in the data layer; data dictionary with GDPR metadata
Deployment contextDev environment (Jupyter/Anaconda) ≠ IT environment (Java/.NET)Define common environment; containerise with Docker; semantic API versioning (/v1/, /v2/)
Development governanceTraining code not reproducible; "runs on my machine" phenomenonVersion code with Git; CI/CD pipelines; reproducible training artifacts
Model governanceNo versioning; model lineage not tracked; metadata unavailableModel registry; versioned endpoints; canary / shadow deployments
MonitoringModels degrade silently; concept drift not detectedMonitor input distributions, output distributions, and latency; alert on drift; backtest periodically

Runtime Deployment Patterns

PatternDescriptionTypical output
Push (batch)Model scheduled to run over a batch of dataResults saved to DB, data lake, Excel, FTP
Pull (API/microservice)Model deployed as REST endpoint, queried on demandJSON predictions consumed by web apps, BI tools

Isolation Levels

  • Virtual environments: Python-level package isolation only.
  • Docker containers: Process + file system isolation above shared OS. Industry standard today.
  • Kubernetes / Kubeflow: Container orchestration at scale; auto-scaling, self-healing.
  • Serverless (Lambda, Azure Functions): No infrastructure management; pay-per-call; cold-start latency.
  • Virtualisation: Full OS stack isolated on hardware emulation; maximum isolation, highest overhead.
⚠ Concept drift: ML models degrade silently. People take actions based on predictions (feedback loop); external world changes (products, promotions, regulation). Without monitoring, a model will happily produce increasingly stale predictions indefinitely.

MLOps → AIops

Moving from MLOps (model deployment pipelines) to AIops involves additional complexity: seamless model selection per query, guardrails and model judges, token caching, and vector databases for retrieval-augmented generation.

7. Hadoop: HDFS & the Distributed File System

Origin & History

  • 2003: Google File System paper → inspired Google MapReduce paper.
  • Hadoop originated in the Nutch search engine (Doug Cutting & Mike Cafarella), named after Cutting's son's toy elephant.
  • 2006: Yahoo! open-sources Hadoop after Cutting joins to work on their search engine.
  • 2008: Yahoo! donates Hadoop to the Apache Software Foundation.
  • Today: the Hadoop hype has passed; Spark and cloud warehouses dominate.

Hadoop's Four Core Modules

ModuleFunction
Hadoop CommonShared utilities and libraries used by other Hadoop modules
HDFSDistributed file system — stores data across commodity nodes in 64 MB blocks with replication
MapReduceProgramming model for parallel processing of large datasets
YARNYet Another Resource Negotiator — cluster resource scheduling and management

HDFS Key Properties

HDFS stores data in 64 MB blocks distributed across data nodes. A name node maintains metadata and makes replication decisions. Default replication factor = 3 (Hadoop 2) → 1.5× overhead via erasure coding (Hadoop 3). HDFS provides distributed storage — not computation. "A massive, distributed C:-drive."
⚠ HDFS is purely a storage system. Storing a file in HDFS and then reading it naively on a single client will still cause the same memory problems as reading it locally. Distributed storage ≠ distributed computing.

SQL on Hadoop — A Cautionary Tale

Every time a new distributed data store became popular, the immediate demand was for SQL access. Apache Hive (2008) translated SQL to MapReduce jobs — effective but extremely slow due to MapReduce overhead. This drove the development of Tez (DAG-based Hive backend), Impala (Cloudera's no-MapReduce SQL engine), and ultimately Spark SQL. The lesson: SQL on Hadoop is a workaround for a fundamental architectural mismatch.

8. MapReduce

Concept

MapReduce stems from functional programming: map applies a function to every element of a list; reduce aggregates a list to a scalar. In Hadoop, it operates over (key, value) pairs. Map tasks can run fully in parallel; reduce tasks run in parallel per key group after a shuffle phase that co-locates all values for the same key.

MapReduce Pipeline

  1. Input split: Input data divided into (key, value) pairs assigned to mappers.
  2. Map: Each mapper applies the map function → emits zero or more (key, value) output pairs.
  3. Shuffle & Sort: All outputs with the same key are routed to the same reducer node.
  4. Reduce: Each reducer applies the reduce function to all values for its key → emits final (key, value) pairs.

Word Count Example

Map: map("two plus two does not equal three") → [(two,1),(plus,1),(two,1),...]
Shuffle: All (two, 1) pairs routed to same reducer.
Reduce: reduce(two, [1,1,1,1]) → [(two, 4)]

The Averaging Pitfall — Associativity Requirement

⚠ The reduce function must be associative and produce the same output structure as the map function — because reduce may be called multiple times on partial results (e.g., when a late mapper finishes). A naive running average fails this: avg(avg(100,200), 300) ≠ avg(100,200,300). The fix: carry a (sum, count) pair as the value, not just the average.
Correct pattern:
Map: (genre, nrPages) → (genre, (nrPages, 1))
Reduce: (key, [(s1,c1),(s2,c2),...]) → (key, (Σsi*ci / Σci, Σci))
This allows correct re-aggregation of partial results at any point.

MapReduce Limitations

  • Hard to program — most tutorials don't go beyond word count.
  • Slow: every intermediate result is written to HDFS disk → massive I/O overhead.
  • Java-native (Python bindings exist but are cumbersome).
  • Not suited for iterative algorithms (ML) — each iteration requires a full MapReduce cycle.
  • "Big does not mean fast" — MapReduce cluster latency often exceeds simple in-memory solutions.

YARN

YARN (Hadoop 2+) separates cluster resource management from the MapReduce execution model. It allows other execution frameworks (Spark, Tez, Flink) to share the same cluster resources without being tied to the MapReduce paradigm.

9. Apache Spark

"2015 was the year of Apache Spark." Spark addresses MapReduce's key weaknesses: 10–100× faster (in-memory vs. disk I/O), easier to program, and natively suited to ML workloads. It replaces the MapReduce execution model with a DAG execution engine supporting cyclic data flow and in-memory computing.

What Spark Keeps vs. Replaces

ComponentSpark's relationship
HDFSCan use HDFS, but also S3, GCS, Cassandra, Hive, flat files — storage-agnostic
YARNCan run on YARN, Mesos, Kubernetes, or standalone
MapReduceReplaced — DAG engine is fundamentally different

Resilient Distributed Datasets (RDDs)

RDDs are Spark's foundational abstraction: an immutable, distributed collection of elements partitioned across cluster nodes. Key properties: fault-tolerant (lineage tracking), lazily evaluated (transformations computed only when an action demands it), in-memory preferred.
Transformations (lazy)Actions (trigger execution)
map, filter, flatMap, union, groupByKey, reduceByKey, join, distinct, sortByKeyreduce, count, first, take(n), collect, saveAsTextFile, foreach, countByKey

SparkSQL, DataFrames & Datasets

SparkSQL introduces DataFrames (distributed collections of named-column rows, similar to pandas) on top of RDDs. The Catalyst query optimiser rewrites queries for maximum efficiency. Since Spark 2.0, DataFrames/Datasets are the primary API — RDDs are low-level and rarely used directly.
AbstractionType safetyLanguage support

DataFrame (= Dataset[Row])Runtime onlyAll four languages
Dataset[T]Compile-time (static)Scala and Java only

MLlib

MLlib is Spark's ML library — "scikit-learn on Spark." Primary API (since Spark 2.0) is the DataFrame-based spark.ml package. Provides algorithms, featurisation, pipelines, and persistence. Since Spark 3, the old RDD-based spark.mllib is in maintenance mode only.

H2O & Sparkling Water

H2O is an open-source, in-memory, distributed ML platform. Its "Flow" web UI, strong algorithm support, and production focus ("Sparkling Water") — integrating with Spark — made it a popular alternative/complement to MLlib. H2O was early to recognise the benefits of combining Spark SQL with H2O's ML algorithms.

10. Streaming Analytics

Three Distinct Streaming Concerns

ConcernDefinitionReality check
Streaming dataData source emits a continuous stream of eventsOften the real requirement — store it and convert to batches
Streaming trainingModel must train continuously on live dataRarely needed; very hard; most models retrain offline periodically
Streaming predictionTrained model scores events in real-time as they arriveOften just a deployment pattern (Push API); model itself is static
⚠ Do you actually have a streaming problem? Netflix: 9M events/second. LinkedIn: 500B events/day. Most organisations have far lower volumes that can be handled with micro-batching or scheduled batch jobs. Assess before building a complex streaming pipeline.

Spark Streaming vs. Structured Streaming

Spark Streaming (legacy)Spark Structured Streaming (current)
Core abstractionDStream — sequence of RDDsUnbounded DataFrame/Table — appended continuously
APIRDD-level transformationsSame SQL/DataFrame API as batch; engine handles incremental execution
Late data handlingComplex; requires manual state managementWatermarking and windowing built-in
RecommendationLegacy; avoid for new projectsPreferred; fully integrated with SparkSQL
Spark Structured Streaming key idea: Treat a live data stream as a table being continuously appended. Express streaming computation identically to batch computation — the Spark SQL engine runs it incrementally. Late-arriving data is handled via event-time watermarks.

Apache Kafka

Kafka is a distributed, durable, high-throughput event broker — not an analytics engine itself. It decouples data producers (apps, sensors) from consumers (Spark, Flink, databases) and provides a historical log that can be replayed. Common pattern: mobile apps → Kafka → Spark Structured Streaming → data lake.

Key Takeaways on the Big Data Landscape

The "big data" hype peaked 2011–2014 and has stabilised. The modern architecture depends on the use case: (1) start with Polars/DuckDB; (2) only add distributed computing if you genuinely need it; (3) cloud-managed warehouses (Snowflake, ClickHouse, Dremio) handle the storage/query layer; (4) Spark remains relevant in enterprise settings; (5) insights matter more than infrastructure.
